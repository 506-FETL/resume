# 商业分析经历证据工作流

本参考适用于商业分析、经营分析、策略运营、WFM、增长项目和 AI 商分产品化经历。它将复杂项目拆成可核验的事实、个人动作、结果性质和面试追问，避免把团队项目写成个人成果，或把方案测算写成已实现结果。

## 何时使用

材料涉及指标、成本、履约、供需、增长、运营复盘、SQL、看板、预测、分层、对照、策略测算、试点推进，或 AI 分析流程时使用。

## 四层事实拆解

先记录事实，再写简历句子：

| 层级     | 要回答的问题                                 | 常见证据                               |
| -------- | -------------------------------------------- | -------------------------------------- |
| 业务问题 | 项目为什么存在，核心矛盾是什么？             | 目标、约束、业务方问题描述             |
| 个人动作 | 用户具体做了什么，交付了什么？               | SQL、口径表、看板、方案、PRD、复盘材料 |
| 结果性质 | 是实际发生、团队结果、阶段信号还是方案测算？ | 结果表、试点记录、复盘、模型输出       |
| 个人边界 | 哪些由用户负责，哪些由团队或其他角色完成？   | 用户确认、分工、评审记录、公开链接     |

只有工具名时，不直接写「熟练使用」。只有团队结果而没有个人动作时，不直接写「主导项目」。

## 结果性质与动词

- **范围或规模**：覆盖的城市、商家、业务线或样本量，不等于个人产出。
- **实际结果**：动作发生后观察到的变化，必须说明时间窗口和指标口径。
- **团队结果**：多人共同完成，表述回到用户负责模块。
- **阶段结果**：只覆盖某批次或仍在推进，不能外推为长期全量结果。
- **方案测算**：模型或假设下的预计影响，使用「测算、预计、模拟」，不能写成「实现」。
- **方法或交付**：SQL、看板、指标体系、PRD、验收用例证明交付，不自动证明业务结果。

完成明确分析或交付时可用「负责、完成、搭建、沉淀」；负责连续模块并推动落地时可用「负责模块、推动、协同推进」；只有口述或待补证据时用「参与过、待确认」。

## 组织简历句子

按此顺序组织：

> 业务问题 → 分析动作 → 判断或取舍 → 交付物或协作动作 → 结果性质 → 个人边界

通用模板：针对【业务问题】，通过【分析动作】拆解【关键指标或约束】，形成【判断、方案或交付物】，协同【相关角色】推进【实际动作】；【结果】属于【实际结果、阶段结果、方案测算或团队使用】，个人负责【明确模块】。

## AI 商分额外检查

涉及 Agent、NL2SQL、知识库或自动化分析流程时，确认原流程痛点、用户负责的知识整理或质量门禁、团队提供的底层模型或数据、实际阶段，以及是否存在验收用例或反馈。没有可靠证据时，不补造准确率、节省工时、用户量、调用量或生产 SLA。

## 面试追问与定稿检查

至少准备：指标为何这样定义、异常如何判断优先级、分析改变了哪项决策、个人与团队如何分工、哪些数字已经发生及哪些只是测算、数据如何验证。

每个强主张必须能回到一条原始事实和证据位置；每个数字说明范围、时间、口径和结果性质；方案测算不得使用「实现、带来、提升了」等已完成动词。
