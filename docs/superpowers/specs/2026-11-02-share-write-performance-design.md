# 分享创建与设置保存性能设计

本期用户已明确授权排查并彻底优化。当前分支实施，不重复索要本期批准；不提交、不推送。实现、验证和用户审查分别记录。开工时工作区干净。

## 证据与目标

云端 resume-share v46 与本地一致，数据库位于 us-east-1。过去 24 小时三次 owner_write 为 4001 / 2295 / 8334 ms；最后一次在首尔执行，网关耗时 8396 ms。管理端 fetch 未指定区域，公开读取已指定数据库区域。保存设置在 UPDATE 成功后仍串行等待分享重读、评论范围、事件写入与广播；即使只改备注也传 allowComments 并触发通知。数据库 publish 的累计平均约 26–36 ms，尚无秒级 SQL 热点或锁等待证据。

新建分享在来源准备完成后仍有插入、发布、废弃回读、可选密码设置、启用、最终回读五次数据库往返。目标是缩短真实成功响应，不提前假报成功，不用缓存正文或降低校验换速度。

## 选定方案与取舍

1. 统一读取与写入的 resume-share 区域配置，继续支持环境变量与 auto。保留 authenticated 请求 Authorization 和 CORS 预检，不把 JWT 放 URL 或降低鉴权。
2. 新增 SECURITY INVOKER 创建 RPC，复用已有发布事务：先按 config → version 锁序，再插入 inactive、调用原 publish、按明确参数激活，返回 id。旧 publish 签名不变，不放宽表/敏感列授权。客户端最终只回读一次真实管理记录。相比只删一次回读，该方案还消除中途可见的未完成普通创建记录；不将现有发布代码复制成第二套实现。
3. 无密码创建在事务内启用；有密码保持 inactive，Edge 设置密码和启用在同一 UPDATE 完成，再最终回读。密码哈希强度、访问令牌失效与限流不变。失败清理仅针对本次已确认创建的链接。
4. 设置 UPDATE 返回实际生效的 release/version/评论策略，供通知复用；持久权限写入继续同步，通知使用现有 background 调度。每次公开和评论访问仍核对真实权限，不能依赖广播承担授权。
5. 保留 current 实时与 history 固定语义、正式投递必须固定版本、岗位归属和修订号检查。对来源准备中的重复工作仅在实证后收敛，不并行越过编辑器保存完成的依赖。

不采用乐观关闭弹窗掩盖等待，不降低 PBKDF2，不新建无界正文缓存，不为小表盲目增加索引，不重写已缓存 JWKS 的认证模块。

## 范围与验收

只改分享写入相关前端、resume-share Edge 和必要新增迁移；原 UI 组件、布局与退出动画保留。独立合成账户和数据验证真实创建/更新，不改真实用户链接。覆盖无密码/有密码、current/history/正式投递、旧发布兼容、跨账户拒绝、失败回滚、密码改变及旧凭据失效、隐私/评论关闭、后台通知、取消与账户切换。

在相同数据与条件下记录前端请求数量、操作开始到完成、Edge 区域和响应时间。数据库先在隔离环境验证角色权限和事务，再部署当前 linked 项目；核对全部迁移账本、函数版本与线上 smoke，清理合成数据。前端类型、格式、构建和真实页面验证通过后交用户审查。所有临时脚本在 tests/share-write，完成后删除。
