# GResume 面试讲述稿重写设计

## 1. 背景与目标

现有飞书文档《项目解读》已经覆盖 GResume 的主要业务能力与大量实现细节，但叙事仍频繁围绕文件、函数和代码片段展开。读者需要先理解代码组织，才能拼出业务能力如何端到端运行，不利于在面试中清晰讲述项目价值、技术决策、实施过程与风险边界。

本次工作创建原文副本并重写，不修改原文。新文档定位为面向前端 / 全栈岗位的项目面试讲述稿，但不按前端、后端拆分职责，而是以完整业务能力为叙事单位，从需求、约束、调研、方案、端到端实现、异常处理、优化、维护和演进等角度解释系统。

重写需要同时达成以下目标：

1. 将普通代码实现翻译成自然语言流程，只有关键判断无法脱离代码解释时才保留短代码片段。
2. 保留原文有效细节，并通过迁移映射避免重组时静默丢失信息。
3. 以当前仓库代码、迁移和验证脚本为事实来源，修正原文中的过时描述与不严谨结论。
4. 深挖 CRDT、状态一致性、实时协作、划词评论、一键分享、AI 智能体、额度结算等能力的难点和亮点。
5. 为核心链路配置架构图、流程图、时序图、状态图、方案对比图和异常恢复图。
6. 每章末尾增加“面试追问与防守”，明确可证明的结论、不能夸大的边界和后续优化方向。

## 2. 受众与叙事原则

目标读者是准备以前端 / 全栈工程师身份介绍 GResume 的候选人，以及希望快速理解项目端到端设计的技术面试官。

正文遵循以下原则：

- 先讲用户问题和业务约束，再讲技术方案。
- 以一次真实操作的时间顺序解释系统，而不是按代码目录罗列模块。
- 浏览器、状态层、同步通道、数据库和 Edge Function 作为同一业务链路中的协作方出现。
- 亮点必须对应真实难题、明确取舍或可验证收益，不能把“使用了某项技术”本身当作亮点。
- 对性能、可靠性、安全性和一致性的结论保持证据强度，不把设计意图表述成线上事实。
- 专有名词首次出现时解释概念和在本项目中的职责；后续再使用缩写。
- 代码名称仅作为证据锚点放在结论附近，不成为段落主语。

## 3. 文档章节架构

副本重组为十二章：

1. **项目全景**：用户问题、四个核心约束、整体业务链路与系统边界。
2. **简历数据生命周期**：创建、编辑、校验、持久化和版本派生，以及唯一事实来源与状态一致性。
3. **编辑与确定性输出**：表单、富文本、模板、A4 分页和 PDF 导出如何形成闭环。
4. **实时协作与离线恢复**：CRDT 选型、字段与富文本双通道、补丁传输、合并、回灌和断网恢复。
5. **划词评论系统**：选区定位、版本基准、锚点迁移、匿名权限、并发写入和性能优化。
6. **一键分享与版本历史**：发布快照、访问控制、口令、评论关系、版本回滚和链接生命周期。
7. **AI 智能体改简历**：工具调用、参数防御、确认写回、多轮循环、流式响应和失败恢复。
8. **ATS 与岗位定制**：结构化诊断、证据定位、原子修复、岗位匹配和版本派生。
9. **AI 额度与服务端信任边界**：预留、交付、结算、释放、对账和并发安全。
10. **求职工作台**：投递看板、首页聚合、活动时间线、模板中心及业务数据联动。
11. **身份、权限与运行基建**：登录态事件流、RLS、Edge Function、Storage、路由和可观测性。
12. **工程交付与系统演进**：目录边界、迁移、验证、性能瓶颈、规模化路线和未解决风险。

原文后端深潜章节中的 MVCC、锁、RLS、索引、Realtime 和 Edge Function 等知识不再作为孤立技术列表保留，而是分配到真正使用这些机制的业务章节。最后一章只总结跨业务的工程治理和系统性风险。

## 4. 单章内容模板

每章按统一结构组织：

1. **场景开场**：用户执行什么操作，业务为什么需要该能力。
2. **核心矛盾**：指出需要同时满足、但天然存在张力的约束。
3. **方案调研**：候选方案、适用条件、被否决原因和最终选择。
4. **核心模型**：事实来源、状态边界、数据身份和关键不变量。
5. **正常链路**：按真实发生顺序详细描述一次端到端操作。
6. **协作关系**：解释各层分别承担什么责任，以及如何互相确认。
7. **异常链路**：断网、并发、超时、重复请求、权限失败和部分成功的处理。
8. **优化与演进**：初始方案的问题、观测方式、定位过程和改进结果。
9. **难点与亮点**：总结问题难度、关键取舍和真正产生价值的方案。
10. **当前不足**：区分未解决、部分解决和仍需运行数据验证的问题。
11. **面试追问与防守**：列出追问、可证明回答、证据、表述边界和下一步优化。

“面试追问与防守”使用以下固定字段：

| 追问 | 可证明的回答 | 证据 | 不能夸大的边界 | 下一步优化 |
|---|---|---|---|---|

## 5. 代码与细节处理规则

普通实现全部转换为自然语言流程，包括输入、状态变化、跨层交互、输出和失败结果。文件名、函数名和表名只作为事实证据，在相关结论后简短注明。

仅以下场景允许保留短代码片段：

- 并发事务、锁顺序或幂等守卫的关键条件。
- CRDT 合并、字段级写入或回声抑制中不可省略的判断。
- 权限边界、计费判定和服务端忽略客户端参数等安全约束。
- 不展示关键分支就无法解释故障原因的历史问题。

每个保留片段必须紧接自然语言解释，说明输入、状态变化、失败路径、设计理由和可替代方案。代码片段不得用于代替流程描述。

原文细节先进入“原章节 / 原结论 → 新章节 / 新位置”的迁移映射。重写完成后逐项检查迁移状态；过时或错误细节不直接删除，而是记录修正原因，并在适当位置解释实现演进。

## 6. 图示设计系统

图示参考用户提供的流程图、阶段总览图、分层架构图和时序图，统一采用以下视觉语言：

- 白色或浅灰背景，大面积留白。
- 深色粗体标题与灰色辅助说明。
- 蓝色表示主链路和核心能力。
- 绿色表示鉴权、成功或入口。
- 紫色表示数据、接口和持久化。
- 橙色表示判断、风险、异常和观测。
- 使用细描边、轻圆角、低饱和填充和清晰箭头。
- 箭头旁直接标注动作、条件或数据，不添加水印。

每个图示点独立选择表达方式：

- **整体架构图**：分层展示业务能力、状态与文档层、同步层、Supabase 能力和外部服务。
- **端到端流程图**：展示单次用户操作从触发到反馈的完整步骤。
- **时序图**：展示实时协作、评论提交、一键分享、AI 流式调用和额度结算等跨系统交互。
- **状态机图**：展示登录态、评论锚点、额度请求和分享链接的生命周期。
- **方案对比图**：展示候选方案、否决理由和最终选择。
- **异常恢复图**：展示断网、冲突、超时、重试、对账和降级路径。
- **事实来源图**：区分权威数据、派生快照、缓存和传输消息。

时序图采用顶部参与者卡片、垂直虚线生命线、蓝色激活条和横向消息箭头。自调用表示组件内部判断，异常分支使用橙色标注。单张图控制参与者数量和纵向长度，复杂链路拆成正常流程与异常恢复流程。

简单时序图和状态图使用 Mermaid；需要接近参考图的分层架构、阶段卡片和复杂流程使用自包含 SVG。每张图在正文中先说明要回答的问题，插图后再逐步解释，避免图文割裂。

每章配置一至三张真正降低理解成本的图；实时协作、划词评论、一键分享和 AI 链路可以配置三至五张。画板插入后导出 PNG 预览，检查文字、连线、留白、尺寸和阅读顺序，不合格则修改后重新验证。

## 7. 事实核验策略

技术事实按以下优先级核验：

1. 当前代码与最新数据库迁移。
2. 数据库验证脚本、回归脚本和配置。
3. 部署脚本与更新日志。
4. README 等工程文档。
5. 原飞书文档。

每个重要结论标记内部证据等级：

- **已证实**：代码、迁移或验证结果能够直接证明。
- **合理推断**：架构可以推导，但缺少运行数据或线上证据。
- **尚未证实**：只有设计意图，不得在面试中说成已经实现或已经解决。

正文不需要展示内部标签，但措辞必须反映证据强度。例如，将没有负载数据支持的“性能显著提升”改为“减少了数据库往返，预期降低链路开销；实际收益仍需基准数据验证”。

## 8. 面试风险审计范围

逐章检查以下高风险问题：

- CRDT 能否覆盖所有并发场景，哪些保证仅是最终收敛。
- Automerge、Yjs、Zustand 和 Postgres 之间是否仍可能产生多事实来源。
- 断网、刷新、跨设备和账号切换时的数据恢复边界。
- Realtime 广播的可靠性、顺序、重放和丢消息补偿。
- 评论锚点迁移误匹配、跨 block 和跨版本的语义稳定性。
- 分享快照不可变性、口令校验、匿名令牌、撤销和过期竞态。
- AI 工具参数、用户确认、重复执行和部分失败的防御。
- 额度预留、结算、释放和对账的幂等边界。
- RLS、SECURITY DEFINER、匿名入口与 Storage 签名 URL 的安全边界。
- A4 分页在字体、浏览器和复杂内容下的稳定性证据。
- 性能结论是否有基准数据，观测指标是否足以证明优化效果。
- 可观测性、告警、CI、恢复演练和容量验证的空白。

## 9. 安全写入与验证

原文保持不变，先通过飞书云空间复制能力创建副本。副本按章节局部更新，不执行整篇 overwrite，避免丢失评论、画板和暂不支持的资源。

每章执行以下闭环：

1. 读取原文对应章节及当前仓库证据。
2. 建立细节迁移映射和事实核验清单。
3. 生成自然语言讲述稿与配套图示。
4. 按 block 写入副本。
5. 重新读取更新范围，检查结构、事实、语气和资源。
6. 导出新画板预览，检查视觉质量和可读性。
7. 修正问题后再进入下一章。

全文完成后执行以下验收：

- 十二章结构完整，标题与目录一致。
- 原文重要细节都有明确去向，错误或过时细节有修正记录。
- 核心能力均包含端到端正常流程和主要异常流程。
- 每章均包含难点、亮点、当前不足和面试追问与防守。
- 图表与正文口径一致，所有画板均可正常预览且没有空白占位。
- 关键结论可追溯到当前实现，不存在把推断写成事实的表述。
- 输出事实错误、薄弱点和高风险面试表述汇总。

## 10. 范围边界

本次只重写飞书文档副本，不修改项目业务代码、数据库迁移或线上配置。核验过程中发现的工程问题记录在文档中，不在本任务中直接修复。

本次不承诺通过现有证据无法证明的线上吞吐量、性能提升比例、零数据丢失、严格一次执行或绝对安全。需要运行数据、压测或恢复演练才能证明的结论会明确标注验证缺口。
