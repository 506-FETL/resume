# 求职看板反馈精简与联系人响应式布局设计

## 背景

求职看板当前在大量普通更新后显示成功 Toast。联系人字段在失焦保存时也会提示“已保存”，连续编辑多个字段会产生重复打扰。同时，联系人卡片固定采用多行布局，在宽抽屉中留白过多，在窄屏下标题和操作区也缺少明确的响应式策略。

部分永久删除入口已使用二次确认，但联系人、手动跟进记录以及列表卡片/表格中的职位删除仍会直接执行，交互规则不一致。

## 目标

- 仅在创建和永久删除成功后显示成功 Toast。
- 保留接口失败和业务规则阻断提示。
- 所有永久删除入口在执行前进行二次确认。
- 联系人卡片在大屏、中屏、小屏下分别采用单行、两列两行和单列布局。
- 不改变现有数据模型、保存时机、Supabase API 或全局 Toast 配置。

## Toast 规则

### 保留

- 创建成功：新增职位、新增联系人、新增手动跟进记录。
- 删除成功：删除职位、联系人、手动跟进记录及批量删除职位。
- 所有接口失败 Toast。
- 业务规则阻断提醒，例如尚未完成当前面试、尚未选择阶段开始时间。

### 移除

- 联系人字段失焦保存成功。
- 下一步跟进保存或清除成功。
- 职位状态切换成功，包括 Offer 和终止流程提示。
- 归档、取消归档、批量归档成功。
- 批量修改状态成功。

本次仅清理 `src/pages/tracker` 范围内的提示，不修改其他页面的反馈策略。

## 删除确认

以下永久删除入口统一使用现有 shadcn `AlertDialog`：

- 联系人删除。
- 手动跟进记录删除；自动生成的状态记录继续不可删除。
- 列表卡片中的职位删除。
- 表格中的职位删除。

职位详情抽屉删除和批量删除已经存在确认流程，保持现状。确认对话框明确展示删除对象；取消不产生请求，确认后才调用删除接口。删除失败时保留原有错误 Toast 和现有数据。

## 联系人响应式布局

联系人列表项由“字段区 + 右侧删除按钮”组成。字段区使用响应式网格：

- 大屏（`lg` 及以上）：姓名、角色、联系方式、备注单行排列，按 `姓名 / 角色 / 联系方式 / 备注` 顺序展示，联系方式和备注获得更多横向空间。
- 中屏（`sm` 至 `lg`）：两列两行，第一行为姓名、角色，第二行为联系方式、备注。
- 小屏（`sm` 以下）：四个字段单列纵向排列。

删除按钮在各断点均位于卡片右上侧，不挤压字段内容。联系人标题区在小屏改为纵向布局，“添加联系人”按钮占满宽度；`sm` 以上恢复左右排列和自适应按钮宽度。

保留现有输入高度、本地受控更新与失焦落库机制。布局调整不改变字段名称、placeholder 或数据结构。

## 状态与错误处理

- 删除对话框使用局部状态保存待删除对象，关闭或取消时清空。
- 删除请求期间沿用组件现有 saving/disabled 状态，避免重复提交。
- 普通保存即使不显示成功 Toast，仍保留现有按钮状态、数据回写和失败反馈。
- 不引入新的全局 store 状态或公共通知抽象。

## 验证

- 运行目标文件 ESLint、`npx tsc --noEmit` 和生产构建。
- 审计 `src/pages/tracker` 中的 Toast，确认成功提示只剩创建和删除。
- 手工验证联系人新增、编辑、删除取消、删除确认和删除失败路径。
- 在小屏、中屏和大屏宽度下检查联系人字段排列、按钮可用性、无溢出或重叠。
- 手工验证列表卡片、表格及跟进记录的删除确认流程。
