# 编辑输入卡顿根因与修复

用户反馈上一轮降低检查频率后，实际书写仍不流畅。本次保持已确认的界面、即时编辑、保存、评论与导出行为，直接在当前分支修复。

## 证据

相同隔离 Chrome、默认模板、六条经历各六段正文，连续输入 36 个字符：检查结果没有更新仍出现 54 个长任务，合计 7,034 ms；输入事件处理时长中位数 139 ms、P95 368 ms。CPU 栈主要是同步 React 渲染、重复评论锚点构建（字素分段与 SHA-256）和富文本解析。

预览订阅整个表单 store，每次渲染重新 normalize 整份数据；分页状态与保存状态因此也产生新的模板上下文。测量与每张纸各挂载一个 runtime，分别计算相同的评论文档和内容模型。即使只修改邮箱，不变的富文本也会重新净化、解析并生成 React 节点。

## 方案

首先消除同一内容的重复工作：预览仅订阅正文相关引用并 memo 数据与子树；同一不可变预览数据的评论节点及内容模型由测量/展示副本共享；富文本只在 HTML、投影模式或元素样式变化时重新净化解析。保持 DOM、净化规则、评论 node key、分页签名与打印尺寸不变。

不延迟保存或把表单改为失焦才写入，不通过关闭预览改善数据。若复测仍有明显输入阻塞，再依据新采样调整渲染调度，并对导出最新内容设严格保护；不能以检查次数下降代替书写流畅度验收。

缓存只驻留浏览器内存，以不可变数据对象和投影日期为键，使用 WeakMap 释放旧简历；不改共享服务端评论协议及哈希算法。

## 后续采样与落实

仅缓存把中位数降到 83 ms，稳定面板边界后仍约 46 ms。把预览改为 `useDeferredValue` 后，CPU 栈确认同步输入主要耗在表单其他控件：整个 section 的订阅让 FormProvider 广播新上下文，CheckFields 也按每次正文更新重新生成相同反馈对象。

表单同步因此拆成无界面的 ResumeFormSync 子组件，复用原有字段级同步及光标保护，仅由它订阅 section；表单父层只读初始化值。字段警告只在检查结果或稳定条目路径变化时更新，普通文字不广播上下文。编辑面板、隐藏检查及分享弹窗使用稳定属性与 memo 阻断无关重绘。此调整应用于所有编辑模块，不只邮箱。

整份预览在停笔 180 ms 后合并更新，并使用 React 可中断渲染；切换简历身份时不沿用旧简历的延迟值。输入仍即时写入 store，既有自动保存时间保持不变。PDF/Word 入口共同检查已提交预览的正文、简历身份和外观引用，预览落后或分页未就绪时不导出旧内容；不放宽原打印签名与字体校验。

## 验收

对相同连续输入比较 input 事件处理时长、长任务和 DOMParser 次数。覆盖普通输入、中文输入法、富文本输入、远端字段同步、保存后重新打开、检查标记清除。共享渲染改动覆盖默认及蓝金模板、短内容/接近页底/多页正文；从真实入口导出 PDF，检查文本、页数、背景开关、评论锚点与最终输入，Word 不遗漏尾字。临时工具放 tests/editor-input-performance，完成后删除。类型、格式、构建均检查。

## 连续粘贴的第二处根因

降低 React 重绘后，连续多段粘贴仍明显卡顿。Chrome timeline 显示 100 次粘贴约触发 103 次布局，布局累计约 5.4 秒、样式重算约 2.6 秒；每次原生光标定位会带起整页约 851 个元素的样式重算。把同一编辑器移出 sidebar 容器、保持其他页面可见后，单次耗时降到约 5 ms，进一步移除宽范围 `:has()` 也得到相同结果。

根因是 sidebar 背景和顶部栏高度通过 `:has()` 查询整个页面的后代节点。ProseMirror 更新段落和根节点 class 时，触发这个大范围依赖失效。修复后，sidebar 背景只查询直属 sidebar 子节点；顶部栏高度直接使用已有的 sidebarOpen 状态，并保持桌面断点、编辑器自适应高度及原过渡效果。

富文本工具栏也从订阅完整 EditorState 改成 Tiptap `useEditorState` 的具体按钮状态选择器；隐藏 AI 浮层不再因页面滚动向所有编辑器发送定位事务。复用现有组件，不更换 UI、不禁用动效。

## 实测结果与边界

环境为本机独立 headless Chrome、Vite 开发服务、合成离线简历（六条经历，每条六段），不改用户简历。性能测试不与构建并发执行。

| 场景                                    | 结果                                                                                   |
| --------------------------------------- | -------------------------------------------------------------------------------------- |
| 普通输入框连续快打 10 秒                | 978 个字符，处理耗时中位数 2.2 ms、P95 4.6 ms，输入期间无超过 50 ms 的长任务           |
| 富文本连续快打 10 秒                    | 879 个字符，中位数 3.4 ms、P95 5.8 ms，输入期间无长任务                                |
| 10 秒连续粘贴 100 次，每次 86 字并换段  | P95 从约 105 ms 降至 8.3 ms，输入期间无长任务；停笔后的预览更新有 105/75 ms 两个长任务 |
| 10 秒连续粘贴 100 次，全部追加到同一段  | P95 23 ms，输入期间无长任务                                                            |
| 10 秒连续粘贴 250 次，每次 86 字并换段  | 累计约 2.1 万字，中位数 4.6 ms、P95 6.5 ms，输入期间无长任务                           |
| 普通输入框连续插入 100 段文本，约 10 秒 | 3,000 字完整保留，输入期间无长任务                                                     |

快打时长来自 Chrome Event Timing 可观测样本（事件阈值 16 ms）；粘贴时长在实际 ProseMirror paste handler 外计时，使用合成 ClipboardEvent/DataTransfer，并非操作系统剪贴板实测。普通输入框批量插入使用浏览器 Input.insertText 路径。各场景均逐字核对实际编辑内容，没有漏字。额外的极端测试中，单段不换行累计超过两万字后仍可出现 50–100 ms 级延迟；同一编辑器移出应用、关闭其余页面后仍能复现。采样主要落在原生光标定位触发的长段落排版，不能把这部分宣称为已经消除。没有用截断正文、强制插入换行或更换字体掩盖问题。

功能回归覆盖中文组合输入、字段更新与光标保持、经历重排/新增/删除、自动保存后刷新、字段标记消失、格式按钮/撤销重做/链接/选择浮层。远端更新由 store 注入模拟，未进行真实双账号云端协作测试。默认与蓝金模板分别验证短内容、接近页底及两页正文，经真实导出入口校验打印副本，再由 Chrome 生成背景关闭/开启共 12 份 PDF，核对文本、页数和末尾内容；Word 同样包含最新尾字。

验收脚本、合成数据和性能采样均临时放在 tests/editor-input-performance，最终删除。测试输出放在已被 Vite 忽略的 `.superpowers/` 子目录，避免写 HTML 触发 full reload 干扰保存及性能测量。
