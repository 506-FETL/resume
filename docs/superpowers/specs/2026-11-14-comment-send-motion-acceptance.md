# 评论发送与长文展示验收

日期：2026-11-14。实施完成；验证完成；最终用户审查待进行。

## 最终行为

- 发送时评论入场一次，成功后原位更新，不重建正文。失败保留内容，重试复用原幂等请求 ID。
- HTTP 响应与实时通知均通过既有服务端评论 ID / 请求 ID 关联临时渲染身份；同一 scope 刷新保持，切换清空。真实业务 ID、权限和后端协议未变。
- 发送状态与操作栏共用一个固定最小高度的区域，以现有 AnimatedContent 切换；重试前把焦点交回常驻容器。
- 长评论超过实际 6 行才显示“展开全文”，展开后可“收起”。收起末行使用原生多行省略号、轻微渐隐与 1px 局部背景模糊；展开后全文清晰。展开状态在发送确认和刷新后保持。

正文复用既有链接识别逻辑，抽到 CommentBody 承担测量与折叠。已检索现有 Collapsible 及官方说明，0 高度开合不适合保留 6 行预览，因此只为该正文容器使用局部高度过渡，保留原公共组件；见[设计](2026-11-14-comment-send-motion-design.md)。

## 复现与浏览器证据

临时夹具挂载正式 CommentsPanelContent、ThreadDetail、CommentTree、CommentComposer、provider、Zustand store、动作与 API 客户端。仅在 HTTP 边界提供符合既有协议的合成响应；没有向真实评论服务发送评论，不修改用户数据。本次验证 UI 与归一化/状态合并，不冒充云端写入端到端验收。

原实现确认成功时，连续帧最多同时存在 2 个正文 article，最终节点与发送时不同，两个容器分别执行退出和进入。修复后同一正文始终为 1 个节点；普通确认样本 104px 高度与 170px 顶部位置保持不变，透明度保持 1。

主场景 18 项通过：

- HTTP 先到两轮，随后实时通知与刷新。
- 实时通知先到，随后 HTTP 回应与刷新。
- 发送失败、键盘重试、重试仍用原请求 ID，焦点不留在退出节点。
- 首次入场尚未结束就确认成功：同一节点继续原入场，没有第二份正文。
- 新线程根评论确认，以及返回线程列表后确认仍复用同一行。
- 长评论默认 6 行，发送确认与刷新后保持展开；两轮键盘开合、快速反向。
- 390px 宽度没有页面横向溢出；聚焦裁切区域内链接自动展开。
- 运行中修改减少动效、减少动效下发送、切换 scope 清理映射、短评论不出现展开按钮。

额外 5 项通过：6/7 行临界、动画中开启减少动效、隐藏链接实际几何可见、两层嵌套回复身份、直接 replaceScope 清理映射。

普通确认、刷新和长文保持状态的样本各采集约 55 帧，正文身份、数量、位置和高度均稳定。快响应样本仍处于第一次合法入场，透明度和位移继续收敛，不能把它计为已完全静止。快速反向样本从 480px 收到中间约 230px 后展开回 480px，验证了中间态和终态。

## 过程中修正的问题

动画中切换减少动效首次失败：展开 50ms 后开启偏好，30ms 后实际高度仍为 366.35px，全文为 384px，还有 1 个活动 CSS 动画。仅改变 transitionDuration 不会结束正在运行的过渡。现在只结束正文容器、箭头和末行渐隐层自身的过渡；复测高度为 384px、活动动画为 0。

按用户第二次补充，将硬裁切改为省略号与轻微模糊。收起时测得 line-clamp=6、144px 可见高度、552px 完整高度、blur=1px；展开后 line-clamp=none、高度 552px、渐隐层透明度 0，收起后恢复 144px。已实际查看 390px 的收起/展开及深浅色截图，通读按钮与状态文案。

初始测试浏览器复用了过期的历史测试认证，另有夹具热更新重复挂载和 favicon 报错。最终切到独立本地域名、完整重载并补空 favicon 后重跑；最终页面没有 error/warning，不把初始环境报错当作通过。

## 动效复核

按 review-animations 逐项检查，仓库的公共预设和减少动效规则优先。

| 原表现                    | 最终表现                     | 依据                  |
| ------------------------- | ---------------------------- | --------------------- |
| 临时身份确认后重播整段    | 同一节点只入场一次           | 两种完成顺序逐帧验证  |
| 状态与操作同时占两行      | 单区先退后进，预留操作行高度 | 高度与位置连续不变    |
| 长文直接撑满面板          | 6 行预览，末行省略与轻微模糊 | 实际渲染与深浅色核对  |
| 减少动效中仍继续 CSS 过渡 | 仅结束本区域自身动画         | 中途切换后 0 活动动画 |

局部高度动画用于长文展开时推动后续评论，不能用 transform 替代实际流式高度；范围只限该段正文。采用公共 200ms 展开、140ms 收起，可快速反向；其他行的既有动画保持。独立源码审查已核对身份映射、长文基础实现和最终省略号增量，没有遗留 P1/P2；动效复核通过。

## 本人头像补充验收

用户继续反馈：本人头像已加载，临时评论仍展示占位。根因是 pending-creations 写死作者为“我”、avatarUrl 为 null。新线程和回复现在入队时同步捕获 user store 中的 ID、昵称和头像；昵称复用已有解析函数。只用于临时展示，不改变写入凭据和服务端作者判定；没有用户资料时保留原回退。

在正式 provider、ThreadDetail、动作、客户端与 store 上，用合成已登录资料和提前加载的测试头像验证；只替换 HTTP 响应，不发送真实评论。5 项通过：

- 首次发送采集 29 帧，其中 27 帧正文已可见，缺少本人头像的可见帧为 0，昵称均一致。
- 发送后改变当前账户资料并执行同 scope 刷新，旧评论仍使用发送时的作者快照。
- 失败重试沿用原请求 ID；从 pending 到成功复用同一 img 节点和头像地址。
- 新建线程同样从首次展示到确认保持本人资料及同一图片节点。
- 没有已加载资料时不误用上一账户头像；实际写入载荷没有新增 author/avatarUrl 字段，只有原创建请求，没有资料读取请求。
