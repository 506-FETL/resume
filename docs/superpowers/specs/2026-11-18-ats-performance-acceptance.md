# ATS 长等待与流终态验收

日期：2026-11-18。属于本期全项目性能排查。临时账号及合成验收简历仅用于隔离验证，本文不记录账号、请求或上游标识。

## 触发与根因

真实「开始检测」入口返回 HTTP 200，但浏览器请求持续 151628.9 ms 后中断。上游输出包括较长思考过程和不完整 JSON，尚未产生模型结束标记；积分请求停留在 `pending / started`。

- 云端 `llm-proxy` v51 的请求处理、流转发、校验及超时常量与本地源码逐字一致，不是漏部署。
- 当前项目为 Free，执行地区为 `ap-northeast-1`。该执行从启动到 `Shutdown / WallClockTime` 恰好 150 秒。200 响应头在约 1.927 秒已发出，不代表检测或结算成功。Supabase 官方规定 Free worker 墙钟上限为 150 秒，付费为 400 秒；本期没有修改套餐或地区。[官方运行限制](https://supabase.com/docs/guides/functions/limits)
- 120 秒计时器一直保留到流结束，但只取消 `fetch` 的 AbortController。已取得的 body reader 没有直接响应取消，最终被平台终止，应用未执行流终态与账本收尾。不能仅凭该现象断言某个 Deno 内部缺陷；本期在实际消费的 reader 上补齐取消。
- ATS 开启思考却未指定强度。DeepSeek 官方当前默认强度为 `high`，`medium` 也映射到 `high`；`low` 仍使用思考模式。长思考与报告生成共同消耗运行时间。[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)、[请求参数及结束标记](https://api-docs.deepseek.com/api/create-chat-completion/)

## 修复边界

- ATS 保留 `thinking: enabled` 和 16384 输出预算，显式使用官方 `reasoning_effort: low`。五个维度、证据定位、建议结构及事实约束不变。
- ATS 强制要求 `finish_reason=stop`、非空正文和完整 JSON 后再进入原报告归一化与保存流程；截断和缺失结束标记仍报错。
- 超时直接取消 reader，停止消费，并沿用原账本事务：未交付释放，已交付结算为 `partial`。客户端取消单独记录，不伪装成正常完成，不自动重试模型。
- 流失败发送可被现有 SSE 消费器识别的错误帧，超时文案为「AI 处理超时，结果未完成，请重试」。失败帧不发送 `[DONE]`，不把内部错误码作为用户文案。
- 正常完成保留真实用量与结束标记。所有终态共用单次结算门禁，并清除计时器和取消监听。

## 已执行验证

- 源码流验证直接调用真实 `createStreamingResponse`，仅替换上游流及账本 I/O 边界。旧实现复现超时不结束 reader、客户端取消误标为上游失败；修复后 6 项通过：无输出超时、已有思考后超时、正常结束及用量、客户端取消、真实 OpenAI SSE 消费器错误提示、缺少结束标记的 `[DONE]`。
- 前端类型检查、Deno 函数类型检查、改动文件 ESLint、Prettier 和 diff 空白检查通过。
- 已部署 `llm-proxy` v52，回读 16 个部署文件与本地逐字一致。没有数据库迁移；本地与云端迁移账本均 79 项，版本完全一致。
- 首轮同一份合成简历、相同模型和地区的真实 low 调用：预留至结算 82.29 秒，`settled / completed`，`finish_reason=stop`，4324 输入 token、5393 输出 token。该数据只证明本样本成功，不是固定提速承诺。该轮采集器未保留完整结果，不能据此宣称报告质量检查通过。
- 第二轮同样本仍出现较长思考：首思考 1.954 秒、首 JSON 79.530 秒；超时前收到 7079 字符思考和 11298 字符不完整 JSON。v52 在客户端测得 121.187 秒时返回明确超时错误，云端及时落为 `settled / partial / upstream_timeout`，没有结束标记或伪造用量，没有保存报告。该结果证明超时故障修复，也说明 `low` 不能保证模型在时限内完成。
- 同次线上日志记录 `stream_failed / upstream_timeout` 为 120754 ms，随后 worker 正常 `EarlyDrop`，没有再触发 `WallClockTime`。
- 原 v51 遗留请求随后由既有 15 分钟过期对账流程结算为 `partial / reservation_expired_after_delivery`。本期保留该补偿机制；正常超时不再依赖它等待十几分钟才收尾。

## 报告语义复查与最后修正

第三轮在 59.853 秒正常完成，首 JSON 15.082 秒，5 个评分维度、5 个 Findings、5 条 Evidence、5 条 Suggestion 全部保留；评分加总一致，所有定位、原文值和改写前值与输入精确匹配，归一化没有丢弃条目。

语义复查发现一项不能验收为通过的问题：模型把 2026-06 判断为未来日期，实际检测发生在 2026-11。此前提示词没有提供当前时间。已补入每次检测的真实 ISO UTC 时刻作为唯一日期基准；没有新增“任意未来日期均错误”的规则，未改变预计毕业等既有语义。错误报告没有保存。

同份完整输出为 11037 字符，把相同对象用 `JSON.stringify` 紧凑序列化后为 6590 字符，原输出含 392 个换行，约 40.3% 字符属于可删除的排版。已要求模型输出完整紧凑 JSON，不减少字段、原文证据或完整建议；该字符差值不等于 token 或等待时间同比下降。

## 最终生产构建的真实入口验收

在独立浏览器会话中登录原合成账号，使用本地生产构建的「选择简历 → 开始检测」，选择同一份验收简历。未通过直接调用内部函数替代本轮 UI 操作，未增加账号额度，也没有应用任何生成建议。

- 浏览器仅发起 1 次模型请求，实际请求确认包含 `thinking: enabled`、`reasoning_effort: low`、16384 输出预算、真实检测时间与紧凑输出要求。执行地区仍为 `ap-northeast-1`。
- 网络端到端耗时为 111.880 秒，正常 `finish_reason=stop`。云端账本为 `settled / completed`，没有 failure code；预留至结算 110.481 秒，记录 4388 输入 token、6608 输出 token，其中模型报告 2953 reasoning token；仅扣除既定 3 点额度。
- 页面显示 56 分、4 项待处理；5 个评分维度加总与总分一致。4 个 Findings 和 5 条 Evidence 全部保留，原始输出及落库结果的证据值、建议 before 和定位均与输入精确匹配。参与评估的栏目与真实输入一致，2026-06 的未来日期误报没有再出现。
- 报告通过正常归一化流程自动保存。刷新后恢复相同 56 分、4 项与完整分析，模型请求总数仍为 1；没有页面错误。
- 原模型给出 5 条建议，其中 3 条误用 `replace_text + string`。既有校验拒绝这类组合，相关 Findings 使用原有的待补充建议兜底，最终保存 4 条建议；所有建议保留待补充信息，没有编造姓名、机构或成果数字。本期没有修改这套校验，也不能把原始输出记为完全遵守建议协议。
- 模型没有遵守紧凑 JSON 要求：实际正文 11188 字符、377 个换行；同对象紧凑序列化为 6932 字符。因此该提示只是一项保留完整内容的优化要求，本轮没有证据证明它缩短了输出或等待时间。
- 验收窗口已关闭。没有新增账号或存储对象；最终报告、验收原账号及合成数据交由本期统一清理。

## 结果与长期约束

实施完成，隔离验证、v52 部署与线上正常/超时两种终态核验通过；用户审查尚未完成。前端已通过本地生产构建实际入口验收，未发布到线上站点。

模型等待仍有明显波动：同样本 `low` 既有正常完成，也有到达 120 秒应用时限的真实请求，不能承诺固定提速或每次成功。已修复的是平台强制终止前缺少可控收尾、部分 JSON 被当作可用结果以及缺失真实日期基准的问题。

后续修改流处理时，必须同时覆盖首字前超时、已有交付后超时、客户端取消、正常完成和缺少模型结束标记。验收须核对客户端可见终态与账本状态，不能以 HTTP 200、已经收到文字或合法但未完整的 JSON 作为成功。模型参数调整仍须保留评分依据、原文证据、事实约束及未完成报告拒绝保存的规则，并分别报告模型等待与应用开销。
