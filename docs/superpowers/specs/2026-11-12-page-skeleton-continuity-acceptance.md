## 触发场景与修复

| 触发场景                       | 根因                                                     | 本轮处理                                                                                            |
| ------------------------------ | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 优化、历史等页面冷进入         | 路由使用四行通用卡片，正式页面又换成业务骨架             | 新增轻量 `page-skeletons`，路由和首次数据等待共用真实区域结构                                       |
| 历史候选列表、正文依次读取     | 候选等待显示两块大灰面板，正文等待才显示版本行和纸张     | 保持真实时间线、详情、A4 占位及容器断点；不同数据阶段不换壳                                         |

| 手机评分依据加载完成大幅收起   | 骨架始终展开，正式报告在手机默认折叠                     | 初始骨架也按同一手机折叠状态显示                                                                    |

| 同账户返回助手                 | bootstrap 每次清空会话和消息                             | 同账户成功视图保留，后台继续读取列表与当前消息，读取时仍禁用发送                                    |
| 助手刷新中离开再返回           | 旧请求结束前 busy 状态仍在，新挂载将其误认为换目标读取   | 用已有 active/pending/requestId 区分同目标后台读取和导航读取；旧 hook 仍受 cancelled 与账户代次保护 |
| 求职列表加载后列重排、主体下移 | 骨架列与真实表格不同，且 28px 刷新槽只在初始化完成后插入 | 复用真实列名、列宽及 680/880/1100px 容器断点；首次就预留同一刷新槽                                  |

历史、优化报告和分享概览的已有成功内容在同目标刷新时保留，失败继续提供原有错误或重试入口。助手刷新失败在当前内容上方给出“对话更新失败，当前内容已保留。”及重试，不把失败当成空会话。恢复另一个已删除目标、首次读取和切账户仍显示对应加载或错误状态。

没有引入新的动效、UI 或缓存库。共享骨架只组合现有 Skeleton、PaperSkeleton、LoadingRegion、PageLayout、Card、Button、Tabs 和轻量配置，不静态引入页面 store、Tiptap、模板运行时或 Automerge/WASM。助手画布持久偏好的读取拆为轻量模块，路由不通过 assistant store 获取它。简历库沿用既有共用骨架；编辑器不再预留默认关闭的编辑栏。全局 fallback 同时审计了身份等待、登录、注册、找回/重置密码和更新日志的入口，没有改认证功能。

## 刷新、失败与账户隔离

助手共核验 14 个状态点：首次成功；返访列表慢；同目标消息慢；消息未完成时离开再返回；更新完成；列表失败保留；列表重试成功；消息失败保留；消息重试成功；当前目标被删除且恢复失败；恢复其他目标重试成功；切 B 读取中；返回 A 读取中；A 重新读取完成。

- 同目标列表和消息慢时，已有消息一直可见，没有“正在加载消息”骨架；消息读取期间 textarea 仍禁用。
- 列表或消息失败均保留当前成功视图，重试实际发起读取并更新内容。
- 原会话被删除、恢复另一会话失败时，不把旧会话消息显示为新会话；重试成功展示正确目标。
- A→B→A 时旧账户内容立即清空，账户代次从 0 递增到 1、2。不存在旧成功缓存跨账户复用。
- 没有使用 `conversation.updatedAt` 永久跳过消息读取，因为工具重试等消息更新不一定更新它；仍执行原消息读取，保留既有 ownsView/账户代次/请求标识，并防止迟到读取覆盖已改变的消息或运行中的流。

优化报告和历史页面分别通过正式 `init(true)` / `reload()` 核验成功内容→慢刷新→请求失败→重试成功。两者在慢刷新和失败时都保留有效数据，不显示首次读取骨架，错误状态可识别，成功重试后清除错误。

主代理独立核验模板筛选：Chromium/WebKit × 1440/390，真实网络等待期间两轮完整收起/展开、35ms 快速反向、桌面分组反向均正常；过渡时长为现有 0.14/0.2s，运行中减少动效后为 0，页面脚本异常为 0。

## 限制与长期约束

本轮慢分包测试暂停的是开发服务器的实际页面模块，慢数据与失败来自网络边界的受控响应，不是线上耗时对比。成功报告、职位、会话和历史元信息经过真实页面显示；历史/助手预览使用合成模板引用，未把缺少真实模板资源的预览当成成功 PDF 排版。没有运行模型生成、正式保存、云端权限或全量 PDF 导出验收；本轮未改这些实现。

后续修改真实页面布局时必须同时更新其轻量骨架，验收分包→数据→内容三阶段，并覆盖同目标刷新、不同目标切换、unknown 身份和运行中减少动效。共享组件不等于连续体验：还应检查父层入场动画、空状态容器间距、默认折叠和完成后才出现的固定槽位。账户代次和真实读取语义不能为隐藏骨架而省略。这些约束由主代理同步到防回归清单。
