# 全项目性能排查与优化

日期：2026-11-18。

## 授权与目标

用户已授权逐页使用、检查 Chrome Performance / Lighthouse、定位串行读取及其他性能根因并完成修复。本期在当前分支实施，沿用现有 UI、动画、数据隔离和导出协议；完成实现和验证后交用户审查，不重复请求本期许可，不推送远端。

## 方案

以生产构建、真实浏览器与临时云端账户建立基线，再按根因拆分修复。单独优化 Lighthouse 分数不能覆盖编辑与保存；机械并发所有请求会破坏保存顺序。因此以实际正文、表单可用和持久化完成为标准，Lighthouse 与 Performance 用于解释等待来源。

检查宣传首页、工作台、简历库、创建/导入、模板、编辑/检查/导出、职业档案、分享/公开阅读、求职、优化、历史、助手、账户与日志。分别记录实际执行、登录门禁、故障验证及未覆盖场景，不能把路由打开等同于所有功能通过。

## 已有证据

生产空工作台 Lighthouse 桌面 94 分，LCP 1528 ms、TBT 65 ms；实际首屏包含约 606 KB 解压 CSS，工作台还下载约 298 KB 的图表相关共享 chunk。构建模块图确认其中含 Recharts、Redux、D3；必须检查真实消费者，按数据与可见性隔离。多套简历字体样式在管理外壳全局导入，需要核对是否阻塞无需文档的页面。

其他请求和交互先测量再决定改动，不凭 select('\*')、文件体积或 await 数量推断问题。

## 约束与验收

- 复用现有 deferred component、Skeleton、缓存和 Zustand；必要动作即时发起，关闭弹窗保留退出与输入状态。
- 成功写后失效、失败重试、账户 A→B→A、旧响应隔离、保存队列与精确模板绑定继续有效。
- 不修改字体参数、打印几何、模型账本或分享授权来换速度。
- 使用隔离合成账户；原始网络报告与凭据放 tests/performance，最终删除测试脚本和临时数据，保留非敏感测量摘要。
- 同机同场景对比生产资源、Lighthouse、Performance 主线程与请求时间。区分公网波动、受控网络、冷/热与开发/生产。
- 执行类型、格式、构建与实际入口回归。若修改后端，完成 linked 云端部署、账本/版本及线上 smoke。
