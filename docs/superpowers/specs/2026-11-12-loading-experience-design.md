# 全项目加载体验评估与调整建议

日期：2026-11-12。代码基线：`4a597582`。

本轮任务是评估全项目加载反馈，参考其他产品的公开形态，决定保留、替换和简化的场景。评估完成后，用户明确授权“按照你的评估，直接落地代码，我来做最后审查”。代码已实施；验证证据见[本轮验收记录](2026-11-12-loading-experience-acceptance.md)，用户最终审查待进行。本文是实施依据，不代表前端已上线。

## 1. 结论

当前问题集中在加载反馈的粒度与生命周期。页面、图片、正文读取、懒加载分包和用户提交复用了相同的转圈表达；一个入口还可能依次经过多个转圈。把它们统一换成骨架也会继续打断用户。

建议采用以下分工：

| 用户正在做什么                     | 推荐反馈                                       | 现有内容如何处理                                     |
| ---------------------------------- | ---------------------------------------------- | ---------------------------------------------------- |
| 首次进入有明确结构的页面或区域     | 与实际布局对应的简洁 Skeleton                  | 标题、导航、已知标签先显示，只有缺少数据的部分占位   |
| 等待缩略图、简历纸张或文件预览     | 固定比例的纸张或媒体占位，完成后淡入           | 名称、时间、操作和周围布局保留                       |
| 刷新同一对象、翻页、筛选           | 保留当前内容，必要时显示一处延迟出现的局部反馈 | 不反复换回骨架；对可能误操作的旧结果暂时禁用相关动作 |
| 保存、删除、创建、上传、确认绑定   | 当前按钮或当前对象的一处 Spinner               | 保留表单、草稿、页面和错误恢复入口                   |
| 自动保存、后台同步                 | 简短状态文字为主，慢操作再显示小 Spinner       | 不覆盖编辑内容、不抢焦点                             |
| AI 生成、识别、较长的导出过程      | 真实阶段、已返回内容、必要的取消或重试         | 已完成的部分持续可见；只有存在可测进度才显示百分比   |
| 已有有效缓存、本地筛选、纯 UI 切换 | 直接展示结果，保留正常过渡                     | 不人为进入 loading                                   |

全屏或整块 PageLoading 只作为无法展示内容结构时的少量兜底。已有骨架的页面需要收敛外围转圈；没有骨架的内容区按实际结构补足。

## 2. 调研依据

调研的是官方设计系统及公开示例，不把它们描述成对各产品登录后所有页面的实测。已在浏览器查看 GitHub Primer 的加载反馈对照，以及 Fluent 2 的 Teams 导航和内容占位示例。

| 产品体系与来源                                                                                                          | 观察到的处理方式                                                                                                 | 本项目采用的判断                                                               |
| ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| [GitHub Primer：Loading](https://primer.style/product/ui-patterns/loading/)                                             | 大内容可用结构占位；列表内容逐项就绪逐项显示；相邻小区域不应各放一个指示器；短暂闪现会制造噪声                   | 减少一屏多圈；按钮提交与页面读取分开；复用已成功加载的数据                     |
| [Microsoft Fluent 2：Skeleton](https://fluent2.microsoft.design/components/web/react/core/skeleton/usage)               | 示例保留 Teams 的导航图标与标签，只为未知内容占位；骨架仅概括头像、标题、副标题等主要结构                        | 不给已知页标题、导航和静态说明再画骨架；不细描每一个按钮和徽章                 |
| [IBM Carbon：Loading](https://www.carbondesignsystem.com/building-blocks/core/patterns/loading)                         | 结构化内容首次读取采用骨架；操作反馈就近放置；弹窗内部可以占位，弹窗自身保持真实外壳；部分图片用固定区域留白即可 | 内容区替换、窗口外壳保持；缩略图用安静的纸张占位；下拉框保持真实控件与明确状态 |
| [Shopify：SkeletonPage 迁移指导](https://shopify.dev/docs/apps/build/app-home/migrate-from-polaris-react/skeleton-page) | 当前 Web Components 没有一一对应的 SkeletonPage；建议真实页面外壳与已知标题先显示，仅未完成区域提示等待          | 不照搬旧版“整页全是骨架”的形式，也不将采用 Skeleton 当作唯一目标               |

这些来源的具体秒数、动画和禁用建议不完全一致。项目继续以自己的数据时序、权限和减少动效要求为准；尤其不采用 Primer 中“减少动效仍继续加载动画”的建议。下文的 200ms 来自本仓库已经实施并验收的简历分页提示，不是外部产品的通用性能结论。

## 3. 盘点口径与证据

使用 TypeScript AST 扫描 `src/` 中的 TS/TSX，并检查调用点周围的状态条件、数据依赖及复用关系：

| 项目             |          静态数量 | 说明                                                                      |
| ---------------- | ----------------: | ------------------------------------------------------------------------- |
| 直接渲染 Spinner | 121 处，95 个文件 | 包含公共组件、通知默认图标、桌面与手机互斥分支；不等于 121 个独立用户场景 |
| 动态选择 Spinner |              1 处 | 求职自动保存反馈通过 `Icon` 渲染，不在直接标签统计中                      |
| PageLoading 调用 |   11 处，7 个文件 | App 内有 5 处，包含互斥分支                                               |
| 延迟组件注册     |   19 处，8 个文件 | 12 个编辑表单加 7 个功能面板，共用一个转圈 fallback                       |
| Skeleton 标签    | 112 处，25 个文件 | 一组骨架通常包含多个标签，不能与 Spinner 数量直接比较覆盖率               |
| `toast.promise`  |              3 处 | 同步与删除等操作级通知，需要按是否已有就地反馈判断是否重复                |

实际复核：独立匿名浏览器访问本地开发服务 `/template`，仅将公开模板缩略图请求延迟 12 秒以观察等待态。1440×1000 视口内同时出现 6 个 Spinner，页面共有 9 个 loading 缩略图；同一纸张中间重复显示模板名，纸张下方仍有名称。390×844 首屏可见 1 个缩略图 Spinner，占据主要预览区；资源就绪后可见 Spinner 归零，页面没有水平溢出。这是受控慢资源的形态复现，不是线上平均耗时、生产性能或卡死证据。

源码确认的另外两条链路：

- `use-assistant-bootstrap.ts` 在取得 conversations 后写入列表，但直到恢复会话的 messages 返回才关闭 `loadingConversations`；列表组件因此继续显示骨架。会话列表与消息区本应各自完成展示。
- `reloadJobs()` 保留旧 jobs 并设置 `loading: true`；Tracker 页面却优先把所有 loading 映射为整块骨架。可用旧内容已经存在，仍被 UI 隐藏。

已核对的历史依据包括：防回归清单全文；11 月 10 日加载图标统一验收；11 月 11 日列表与加载提示验收；10 月 23 日模板加载规格与计划；11 月 2 日编辑内部加载规格与验收。另定向读取了分享/构建与全站请求链路验收。没有将历史通过记录当成本次全流程验证，也没有声称已读取全部历史文档。

## 4. 主要根因

### 4.1 统一了样式，却没有区分等待类型

11 月 10 日统一的是图标；11 月 11 日又将一批短读取改为仅显示 Spinner。这些改动解决了风格与重复文案问题，但让内容占位、元信息读取和操作提交更加相似。最新需求要求重新判断使用场景，统一图标的约定继续适用于确实需要 Spinner 的地方。

### 4.2 通用 fallback 放大了使用范围

`App.tsx` 的路由、`createDeferredComponent` 的 19 个注册入口及 `TemplateResourceStatus` 的多个消费者都默认显示转圈。冷路径可能经历“路由转圈 → 内容读取转圈 → 模板/图片转圈”。具体出现次数取决于缓存与请求是否重叠，不能把源码层数当作每次必现次数。

### 4.3 小元信息争抢注意力

模板名、关联岗位、公司规则、版本数、图表和缩略图各有指示器。多个条目同时读取时形成连续运动。小段文本可以用等宽占位，已有数据则继续显示，不需要给每个字段一个圈。

### 4.4 首次加载与刷新混用

求职列表已有数据却回到骨架；部分列表标题和计数仍叠加转圈。另一方面，我的简历已经采用“首次骨架、刷新保留、缓存同步命中、提示延后 200ms”，分享列表及历史同目标刷新也已有保留内容的逻辑，应保留这些正确实现。

## 5. 逐模块决定

### 5.1 页面与路由

| 场景                           | 决定               | 具体处理                                                                                                |
| ------------------------------ | ------------------ | ------------------------------------------------------------------------------------------------------- |
| 普通工作台路由分包             | 替换               | 保留 DashboardShell；按目标页结构提供轻量内容占位。新路由外壳与后续数据骨架保持一致，避免转圈后再换骨架 |
| DashboardShell 首次下载        | 收敛               | 只保留必要的应用初始化兜底；不要为了骨架静态导入整套页面或编辑器                                        |
| 密码恢复导航等待               | 保留兜底           | 仍等待真实会话恢复；明确读屏名称。不能预先挂载需要新权限的页面                                          |
| 岗位上下文归属确认             | 替换视觉，保留门禁 | 展示目标内容的中性占位；归属未完成前不挂载编辑、优化、历史消费者                                        |
| 编辑器首次读文档               | 替换               | 纸张占位及编辑布局提示，标题与工具栏按实际可用信息展示；文档真源、旧保存队列与初始化顺序不变            |
| 公开分享首次打开               | 替换               | 中性阅读区/纸张占位；密码、失效、失败与正文分支仍独立，绝不提前展示旧私密正文                           |
| 登录、注册、找回、重设密码页面 | 保留操作反馈       | 表单提交只在提交按钮显示 Spinner，不把表单换成骨架                                                      |

### 5.2 首页

保持现有布局、三提醒配色、真实简历缩略图、待办开放边框及模块并行读取。

| 场景                 | 决定                     | 具体处理                                                            |
| -------------------- | ------------------------ | ------------------------------------------------------------------- |
| 最近简历首次列表读取 | 替换为条目骨架           | 按最多两份的现有“左纸张、右信息”结构占位，保留标题和查看全部        |
| 最近简历缩略图       | 替换为纸张占位           | 复用简历库真实成品缓存，图片未好不影响名称与继续编辑                |
| 面试、跟进、重点关注 | 替换为两行内容骨架       | 标题、图标、查看全部常驻，各模块独立完成展示                        |
| 三张图表             | 替换为安静的图表区域占位 | 保持 140px 的约定区域，不画假的折线、数值或评分；同源数据不重复转圈 |
| 最近动态             | 替换为时间线行骨架       | 沿用已有“有 events 优先展示”的条件                                  |
| 待办、统计           | 保留并精简现有骨架       | 已知标签直接显示，只占位未知内容；不增加整页 loading                |

| 模板目录/创建向导/模板切换缩略图 | 替换                   | 共用轻量纸张占位，固定实际比例；图片解码完成再淡入，错误和重试继续显示                     |

| 创建向导读取草稿                 | 替换                   | 保留标题、关闭和入口布局，只占位真正待恢复区域；不提前开放依赖草稿身份的提交               |
| 向导简历候选、本地同步候选       | 替换内容区占位         | 列表用条目骨架；若最终是 Select，就保留真实控件并显示控件内状态                            |
| 文件读取和 AI 识别               | 保留阶段反馈           | 当前已有“读取文件/识别填充”和取消入口，继续使用单处 Spinner；不伪造百分比                  |
| 创建、绑定岗位、同步到云端       | 保留操作反馈           | 等真实保存成功才完成，未知结果仍沿用原操作身份与恢复机制                                   |

| 公司、简历、历史版本选择器            | 保留控件级等待，去重   | 文字/已选项常驻，同一读取在控件、下方和下拉层只保留一个主要反馈；不把 loading 当“无结果”                   |
| 绑定、推进、跟进保存、投递留档        | 保留                   | Spinner 靠近触发按钮，未持久化前不能显示已完成或提前关窗                                                   |
| 自动保存                              | 简化                   | 现有文字状态与重试保留，快保存不闪圈；读屏状态即时同步                                                     |
| 助手初次会话列表与消息                | 保留骨架，解除无关等待 | conversations 到达后列表立即显示，messages 继续在消息区等待；保留请求代次与用户主动导航保护                |
| 助手切换会话                          | 减少重复反馈           | 目标会话行保留一处延迟忙碌反馈；旧会话可暂留时必须仍明确归属旧会话，输入不得发往错误目标；否则仅替换消息区 |
| 助手历史追加/搜索更多                 | 保留局部追加反馈       | 不清空已有消息和搜索结果；成功后保持滚动位置                                                               |
| 助手生成与工具执行                    | 保留已有阶段反馈       | 优先展示真实流式内容、停止/失败状态；不把生成回复当作读取列表                                              |

### 5.7 账户资料、通知及其他

资料页首次未知字段继续用骨架，已知“个人资料”等标题及设置名称直接显示。更新姓名、密码、头像等提交保留按钮 Spinner。头像已有图像在上传时保留，裁剪窗口不换成整块等待页。

Sonner 的公共加载图标保留。仅在任务已转到后台或当前没有其他清晰反馈时显示持续加载通知；同一提交同时有按钮圈、行内圈和 toast 圈时只保留主要反馈，成功/失败通知继续按实际结果显示。

宣传页、更新日志和错误页没有额外业务加载问题；只涉及共享路由分包 fallback，不额外增加骨架或动画。

## 6. 建议方案与替代方案

1. **推荐：按场景治理。** 先收敛共享入口，再处理重复缩略图与聚合页面，最后调整刷新条件与控件细节。既解决转圈密度，也保留必要反馈。
2. **仅替换大块 Spinner。** 改动较小，但路由、多字段转圈和刷新回骨架仍然存在，用户仍会感到频繁等待。
3. **全站统一 Skeleton 或取消所有 loading。** 不采用。前者把操作提交伪装成内容读取，后者让用户无法判断保存、识别或导出是否执行；二者都不能处理失败与重试。

本轮不提出后端改造、预加载所有页面、额外缓存体系或依赖升级。按需加载和权限门禁继续保留。

## 7. 实施约束

- 复用已有 `Skeleton`、`Spinner`、`AnimatedContent`、`PageLayout`、Button、Select、Dialog、Alert 与 Empty。已有组件足够，不引入新的 skeleton/spinner 库。
- `createDeferredComponent` 增加由调用方提供的轻量 fallback 能力；错误重试与模块缓存继续由原边界管理。占位模块不能经页面 barrel 带入 Tiptap、Automerge 或分页引擎。
- 共用纸张占位与少数列表/文本组合，不建立任意配置生成整页骨架的框架。页面特殊骨架放对应 `components/`，不在 `src/pages` 制造错误路由。
- 首次内容读取立即保留占位几何。已有内容刷新或短操作的次级转圈沿用 200ms 延后显示；请求、禁用和读屏状态立即开始，结果一到立即结束，不增加最短展示时间。
- 每个独立区域只设一处加载语义；骨架装饰对读屏隐藏，不产生可聚焦假控件，不反复播报每行。区域完成即展示，不用一个总 loading 等所有模块。
- 动效复用公共缓动/时长及 `useReducedMotion()`；骨架明暗变化克制，减少动效时静态显示，运行中切换偏好立即生效。转换保持尺寸，图片不通过纵向拉伸进场。
- 已有内容只能在同账户、同目标、有效授权范围内保留。切换账户或目标不显示上一对象冒充新对象；公开分享权限失效立即走原清空/密码分支。
- 错误、未知、首次加载和真实空结果独立。对当前发现的公开分享网络失败与“链接不可用”共用分支，以及助手初始化失败后可能显示空列表的问题，实施前应补相应失败态验收，不能直接把缺数据视为成功空结果。
- 不修改保存队列、操作幂等、打印布局或分页算法。骨架只属于 UI 外层，不进入测量页、打印副本或导出正文。

以下三个优先级均已获用户授权实施，按同一轮工作完成，不作为另行开启的产品期次。任务计划见 [实施计划](../plans/2026-11-12-loading-experience.md)。

| 顺序 | 范围                                            | 完成的可观察结果                                                           |
| ---- | ----------------------------------------------- | -------------------------------------------------------------------------- |
| P0   | 路由/延迟面板、模板与简历缩略图、首页和优化报告 | 常见读取不再整块转圈；模板慢图首屏没有逐卡 Spinner；已知标题与导航持续可见 |
| P1   | 求职刷新、助手独立就绪、历史计数、各种详情读取  | 有结果不反复换骨架；会话列表不等消息；不出现多处同义等待                   |
| P2   | Select 重复提示、自动保存频率、操作通知         | 一项操作只有一处主要忙碌反馈，短任务不闪圈，失败可恢复                     |

验收覆盖：

- 冷/热路由、缓存命中、200ms 内快响应、明确慢响应、失败与重试、取消和迟到响应；记录出现了什么占位、内容何时真正可用，不用“Spinner 数量变少”代表请求提速。
- 首页分别延迟 jobs、简历、报告等数据，核对其他模块先展示；助手列表成功而消息慢/失败时，列表仍可见和可导航。
- 求职已有列表刷新：DOM/滚动保留、错误重试、旧结果动作边界正确；简历库继续回归 10/10/3、回页零请求、固定页脚与失败留页。
- 1440/768/390/320px、320×400 短屏、深浅色；骨架与正式内容的主尺寸、滚动归属和页头位置匹配。
- 弹窗两轮完整开关、退出途中重开、慢分包及真实分包失败；输入、草稿、预览与焦点保留。没有可见内容的假成功不算通过。
- 运行中开启/关闭减少动效，读屏语义与键盘操作；不依赖截图判断动画中间状态。
- 登录/创建/保存/删除/恢复/上传/分享设置/导出等仍等待真实结果。用隔离数据验证，不向真实用户数据或模型请求制造测试任务。
- 生产构建核对轻量 fallback 没有带入编辑重依赖；前端未发布时明确记录。仅当触及实际打印/分页源头时按模板维护约定执行相应 PDF 矩阵。
