# 手机端求职跟进、分享发布与 AI 助手稳定性设计

## 1. 背景与目标

本轮处理六项问题，并以手机端体验为主要设计边界：

1. 更换分享版本时 `publish_resume_share_release` 返回 504，发布按钮长时间保持加载状态；
2. 手机端求职跟进的统计卡占用过多纵向空间，挤压看板与列表；
3. 手机端职位详情 Drawer 的信息和操作层级不合理；
4. 所有底部 Drawer 统一固定为屏幕高度的 70%，所有 Drawer 移除右上角 X；
5. AI 助手代码块在浅色模式下文字与背景对比异常；
6. AI 助手搜索因 cmdk 缺少 Store 上下文而崩溃。

成功标准：

- 分享链接能原子切换到任一有效版本，不再出现必然的 stale snapshot 与锁队列；
- 分享页只返回已脱敏的发布快照，隐藏区块不会通过匿名接口公开；
- 手机端统计区默认保持一行紧凑摘要，主要内容获得更多视口空间；
- 手机端职位详情固定为 `70dvh`，内容可滚动，底部主操作不会遮挡正文；
- 所有纵向底部 Drawer 固定 `70dvh`，横向侧边 Drawer继续保持全高；
- 所有 Drawer 不再显示右上角 X，同时保留遮罩、Esc、下滑手势和已有文字按钮等关闭方式；
- AI 搜索正常打开、输入与选择；代码块在浅色和深色模式下均清晰可读。

## 2. 分享发布根因与安全边界

### 2.1 504 的实际根因

客户端在构造公开分享时会移除隐藏简历区块和 `templateBinding`，再把公开快照作为 `p_snapshot` 发送给数据库。当前 RPC 却把它与 `resume_config_versions.snapshot` 的完整版本快照做 JSON 全量相等比较，因此正常发布也会触发 `stale version snapshot`。

数据库日志同时显示，同一分享链接的连续调用会在 `resume_shares ... FOR UPDATE` 上排队。前面的调用抛错或等待时，后续请求继续积压，最终由网关表现为 504。该问题不是正常 SQL 执行本身耗时过长，因此不通过提高网关超时时间处理。

### 2.2 公开快照泄露

当前 `resume-share` 匿名读取路径虽然查询了当前 release，却返回 `version.snapshot`。这会绕过发布时的隐藏区块脱敏，属于必须与 504 一起修复的公开数据边界问题。

### 2.3 方案 A：修复现有原子 RPC

采用已批准的方案 A：

- RPC 继续校验登录身份、分享链接归属、归档状态、版本归属、来源元数据、模板清单和评论锚点；
- 公开 release 与 `resume_shares.snapshot` 保存 `p_snapshot`，不再用完整版本快照覆盖公开快照；
- `p_snapshot` 必须是 JSON object，且公开模板清单继续进行 object 校验；
- 评论 scope 仍绑定完整版本，客户端从完整版本生成评论锚点，再单独生成公开快照，避免评论身份随隐藏区块变化；
- RPC 设置短 `lock_timeout`，锁竞争时快速失败，不让请求排队到网关超时；
- 客户端按 share id 复用同一进行中的发布 Promise，并用请求超时恢复 UI；
- `resume-share` 匿名响应只返回 `currentRelease.snapshot`。

同一用户拥有自己的分享链接和版本，允许其发布客户端生成的公开投影不会扩大跨用户权限；数据库仍不接受其他用户的版本或分享链接。服务端重建公开投影属于更大范围的 Edge Function 重构，不纳入本轮。

## 3. 手机端求职跟进

### 3.1 紧凑统计摘要

桌面端 Overview 保持现状。手机端单独渲染一条紧凑摘要：

- 左侧显示响应率；
- 中间显示已投递、面试中和 Offer，点击仍沿用现有指标筛选；
- 右侧为展开按钮；
- 默认隐藏待跟进，展开后显示完整的待跟进指标；
- 选中指标继续使用明确的激活态，不改变 Store 的筛选语义。

### 3.2 职位详情 Drawer

手机端职位详情按内容优先级重排：

1. 固定头部：状态、职位、公司、地点和必要元信息；
2. 正文滚动区：跟进、阶段详情、简历与联系人；
3. 固定底部操作区：当前阶段的主操作和“更多”。

手机端头部不再同时堆放阶段推进、编辑和更多按钮。编辑、回退、终止、归档与删除收进“更多”；阶段推进保留为底部主按钮。面试、Offer 或终止状态没有直接下一阶段时，主按钮切换到对应详情内容，而不是成为无效按钮。桌面端原有头部工具栏保持不变。

## 4. Drawer 全局规则

共享 `DrawerContent` 按手势轴设置尺寸：

- 纵向 Drawer：`--drawer-content-height: 70dvh` 且最大高度同为 `70dvh`；
- 横向 Drawer：保留现有全高与业务宽度；
- 各业务调用点移除 60vh、80dvh、92dvh、94dvh、固定像素高度和接近全屏的纵向覆盖值，避免优先级冲突。

右上角图标关闭入口从评论、AI 历史、AI 画布、职位详情、移动分享、移动排序和高级工具 Drawer 中移除。底部的“取消”“关闭”“确认”等文字按钮属于业务操作，不受此规则影响。桌面 Dialog 不属于 Drawer，保持其原有关闭设计。

## 5. AI 助手

### 5.1 搜索崩溃

共享 `CommandDialog` 当前把 `CommandInput` 等子组件直接放进 Dialog，缺少 cmdk 的 `<Command>` Provider；传入的 `commandProps` 又错误落到 Dialog props 上。修复后：

- `CommandDialog` 明确声明 `commandProps`；
- DialogContent 内用 `<Command {...commandProps}>` 包裹所有 children；
- 会话搜索继续使用 `shouldFilter: false`，保留服务端搜索与分页语义。

### 5.2 浅色代码块

代码块处于 Typography 的 `prose` 容器内，`prose pre` 背景与 Shiki 双主题内联颜色发生冲突。修复后：

- `CodeBlock` 根节点使用 `not-prose` 隔离文章排版规则；
- 代码块增加稳定的作用域标记；
- Shiki `pre` 背景使用外层容器背景，深色模式显式应用 `--shiki-dark`；
- 保留行号、复制、下载、水平滚动和无高亮 fallback。

## 6. 错误处理与状态恢复

- 分享发布继续由 Zustand `pendingShareIds` 阻止业务层重复提交；底层再按 share id 合并并发 Promise，覆盖多个调用入口；
- RPC 调用使用有限超时，超时、锁冲突和一般服务错误转换为可理解的中文错误；
- Dialog 的 `submitting` 与 Store pending 均在 `finally` 中清理；失败后不关闭 Dialog，允许用户直接重试；
- 任何失败都不得留下永久 Spinner。

## 7. 验证策略

静态与构建验证：

- TypeScript `tsc --noEmit`；
- 仅针对本轮文件运行 ESLint，避免把既有全仓基线误报为本轮回归；
- 生产构建；
- `git diff --check`；
- 源码约束检查：匿名接口不得返回 `version.snapshot`，RPC release 不得写入 `v_version.snapshot`，纵向 Drawer 不得残留业务高度覆盖，Drawer 头部不再渲染 X。

交互验证：

1. 390×844 手机视口检查统计摘要默认高度、展开状态和筛选；
2. 打开职位详情，确认 70% 高度、正文滚动、底部操作区与更多菜单；
3. 抽查历史详情、评论、移动分享、移动排序、ATS 工具等底部 Drawer；
4. 抽查 AI 历史/画布和桌面职位详情等侧边 Drawer 仍保持全高；
5. AI 搜索完成打开、输入、分页和选择，不出现 `subscribe` 异常；
6. AI 代码块在浅色与深色模式下均可读。

数据库/服务验证在迁移与 Edge Function 部署后执行：切换两个版本、并发重复发布、匿名读取隐藏区块。未部署前的本地静态与构建结果不能表述为线上已修复。
