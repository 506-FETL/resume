# 简历编辑首屏 LCP 修复

日期：2026-11-14。用户已授权在 Chrome 排查并修复。本期当前分支实施，保留原暂存改动，不提交或推送；实施、验证与用户审查分别记录。

## 证据与目标

用户 Chrome 的本地开发页 `/resume/editor` 显示 LCP 4.36 秒，元素为正文段落。实际完整 Performance 跟踪中，正文 GET 在导航后 1,787 ms 才发出，完整响应到 3,984 ms；外观请求同时启动。之后约 368 ms 的长任务包含 Automerge 导入，随后还有 116 / 143 ms 的渲染任务。评论请求从 4,751 ms 开始，不阻塞前面的正文读取。初步 CPU 样本曾指向文本解析，随后对真实 DOMParser 调用直接计时，221 次总计仅约 1–2 ms，因此排除此项，不修改文本转换。启动段另有三个浏览器扩展脚本的 EvaluateScript 合计约 366 ms；开发模块、扩展和公网传输应分别归因。

自动浏览器控制期间的跟踪出现面积约 89,860 的 IMG 候选，导致指标变成 0.12 秒，与真实正文出现不符；不能将其作为收益。采用原生 Chrome 刷新与页面内临时 PerformanceObserver 复测，记录真实候选、正文出现和请求时刻。临时探针仅存在 tests 下，结束清理。

## 方案与取舍

保留原加载 hook、store 与所有门禁，把页面入口变成轻量的加载控制层；原工作区使用已有 createDeferredComponent 并行加载，保留局部失败与重试。hook 在入口提交后立即开始文档流程，工作区分包下载期间仍展示原来的 RouteSkeleton。工作区接收同一层传下来的 loading/currentUser，不复制 hook，也不重复读取。已有延迟组件增加可选的原样 fallback，默认调用行为不变；此处直接复用 RouteSkeleton，不额外添加 padding 或父层动效。加载 hook 和保存 slice 改用实际 config 模块，避免经过全量 resume barrel 引入无关查询和恢复模块。

首轮前台实测发现，单独拆分仍接近 4 秒。尝试主入口路由预取后，请求启动没有稳定提前，已撤回该试验。进一步在真实 getSession 调用边界计时，头像与用户名 hook 在开发模式首屏重复调用 8 次；文档读取在认证锁后等待约 220 ms。复用已有 useUserStore 的 onAuthStateChange 订阅，展示 hook 不再各自读取和订阅 session。保留原 undefined 返回值、头像/昵称解析，以及文档读取和 SDK 请求的必要身份检查；实测该等待缩短到 13 ms。

不修改文本净化、检查规则、CRDT 导入、签名、分页与导出逻辑。生产构建核对新入口的静态闭包，避免只写 lazy 却仍经其他导入拉入工作区。

其他选择：只调整预构建只能改善开发环境；新增正文缓存或改写 CRDT 存储会扩大新鲜度和兼容范围。本期不采用。真实网络仍是主要耗时之一，不能保证每次都低于固定秒数。

## 验收

1. 同一 Chrome、同一真实简历、同一视口，记录原生刷新 LCP 候选、正文时间、正文请求起止，至少前后两轮；将公网波动与启动等待分开。
2. 生产构建核对入口/工作区的真实分包关系；慢工作区加载不阻挡文档流程。不开启下一期重构，不改变协作和持久化接口。
3. 页面必须处于前台且 LCP 元素属于正文；排除锁屏、后台和控制工具光标污染的样本。
4. 实际编辑入口、返回重进、检查与评论开关；使用合成离线简历验证保存重开。25 个真实用户 hook 消费者验证 unknown、A→B→A、退出与零重复 session 读取。用户真实正文不修改。
5. TypeScript、定向 lint、Prettier/layout、生产 build、format:check；清理本期 tests 和诊断入口，记录限制。
