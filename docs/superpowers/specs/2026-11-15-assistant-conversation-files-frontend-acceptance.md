# 当前对话附件前端隔离验收

日期：2026-11-15。依据[本期设计](2026-11-15-assistant-conversation-files-design.md)和[实现计划](../plans/2026-11-15-assistant-conversation-files.md)。后端隔离验证另见[后端验收](2026-11-15-assistant-conversation-files-backend-acceptance.md)。

## 状态与验证边界

- 前端实施完成；本记录中的 7 组隔离浏览器验收通过。
- 本记录只证明前端在受控请求顺序和响应下的行为，不作为云端迁移、Storage、RLS 或模型调用的证据。主任务的真实页面与线上联调另行记录。
- 用户审查待进行。没有 commit 或 push，也没有发布前端。

使用已有 Vite 开发服务 `http://127.0.0.1:5173`，通过本机 Playwright 1.59.1 启动独立无头 Chromium；每组使用新的浏览器上下文，没有接管用户或其他代理的页面。

夹具直接运行真实 `useComposerUploads`、`useChatStream`、`useSourceScope`、助手草稿 store、来源 store、上传解析与 API。文件由浏览器文件输入选择，两份 TXT 使用实际字节提取、哈希和 FormData 保存流程。夹具只提供用于操作这些模块的简单界面，没有复制上传或草稿业务逻辑。

Supabase 请求在 HTTP 边界全部拦截，提供固定测试会话、目录和保存结果；不连接真实数据库、Storage 或模型。会话切换调用正式 store 动作，账户切换通过测试用户 store 触发真实账户代次与取消订阅。文字输入、文件选择、任务重试和移除使用浏览器操作。

## 7 组实际结果

### 1. 双文件、发送拦截、草稿与目录隔离

在空对话填写草稿并添加一条简历引用，同时选择两份 TXT。挂起会话创建时，确认只有一次创建请求、上传计数为 2，输入仍可修改。放行创建、继续挂起保存时，当前会话 ID 与预留 ID 一致，草稿和原简历引用保留。

分别在准备会话和保存文件阶段调用真实 `sendMessage`，两次均返回 `false`。未出现消息写入或模型请求。

保存完成前切到 B 对话并填写 B 的草稿，放行两份保存后，B 的文字保持不变、引用数仍为 0。回到 A，恢复创建期间输入的文字，以及原简历引用和两份附件，共 3 条引用。两次保存均携带 A 的 `conversationId`。

目录断言：`loadLibraryScope` 只返回原有职业档案；A 的范围为档案加两份附件；B 的范围只含原档案。查询仅投影 `id,name,current_version_id,updated_at`，并实际携带 `conversation_id=is.null` 或对应会话的 `eq` 条件。重复读取已成功的目录与范围没有新增网络请求。

### 2. 创建结果未知后的稳定重试

在 HTTP 夹具中模拟创建已写入，但响应返回 500；保留模拟服务端的会话行。任务进入失败状态后点击重试，第二次创建使用完全相同的会话 ID，收到 `23505` 后由真实 API 回读已有行。

断言两次创建请求对应同一 ID，模拟服务端只保留一个会话；后续附件保存沿用原 `operationId` 和会话 ID，草稿文字保留。此项验证错误响应后的重试分支，不声称模拟了真实公网断连或真实数据库事务。

### 3. 创建未完成时离开并再次新建

挂起最初空对话的创建，先切到 B，再打开新的空对话。新空对话的草稿为空，填写另一段文字后才放行旧创建。

旧请求完成后，当前视图仍为空对话，后来输入的文字和空引用不变。进入旧请求创建的会话后，恢复最初的草稿与附件。此项证明草稿迁移依赖预留目标，而不是根据上传计数猜测用户是否切换了视图。

### 4. 创建等待期间切换账户

保持 A 的创建响应挂起，将测试用户 store 切为 B，再放行旧响应。真实账户代次变化触发取消。

断言后续文件 `save` 请求为 0，当前会话仍为空，引用数和上传计数均为 0。此项覆盖前端取消与迟到回填，不代替真实登录切换、服务端鉴权或跨账户 RLS 检查。

### 5. 已有会话上传与队列状态

在已有 B 会话中将队列设为继续状态，再选择文件并等待保存完成。

断言没有创建会话请求，保存携带 B 的 ID，成功引用原文件后 `queuePaused` 仍为 `false`。上传回填没有因为复用草稿恢复函数而暂停原有队列。

### 6. 创建期间移除最后一个文件

填写文字并挂起创建，点击任务的“移除”，随后放行旧响应。

断言上传计数归零、当前会话仍为空、草稿文字保留，文件保存请求为 0。此项验证取消迟到接入和解除发送阻塞，不证明已经发出的数据库创建请求一定被服务端回滚。

### 7. 目录在途复用与失败恢复

使目录缓存失效，同时调用两次 `loadLibraryScope`，确认返回同一个在途 Promise。模拟该次请求返回 500，两位消费者收到失败。

之后再次显式读取，正常返回原有档案。失败没有被缓存成成功空目录。这里验证的是实际目录函数的重试，未把它描述为完整页面“重试”按钮验收。

## 执行记录与局限

最终执行命令为 `node tests/conversation-files-frontend/run.mjs`，退出码为 0，输出 7 组通过。完成后 `git diff --check` 退出码为 0。

补充真实 `useChatStream` 后，首次运行因夹具未配置它初始化时的 `get_ai_quota` 请求而失败。补齐该 HTTP 拦截后完整重跑 7 组通过；未修改生产逻辑来绕过失败，也未把失败那次记为通过。

本记录未覆盖真实页面的 320/390/1440 布局、菜单键盘与焦点恢复、两轮浮层开关、反向切换和减少动效；也未执行真实模型读取、工具重试越界、原件预览与下载、会话删除清理、上传成功后的整页刷新。它们需要主任务的实际入口与线上证据，不能由本次 hook 夹具代替。

## 保留的约束与清理

原问题由上传缺少会话归属、完成后直接写当前草稿造成。后续必须保留稳定会话 ID、冻结 owner、显式草稿迁移、原会话回填和运行前归属核对；多文件、离开后返回、未知结果重试及账户切换应继续作为回归场景。

复用草稿恢复函数还会默认暂停队列，因此普通上传回填明确保留当前队列状态；只有原有恢复任务继续使用暂停语义。验收方法为第 5 组的实际状态断言。

夹具、脚本和非敏感结果曾统一放在 `tests/conversation-files-frontend/`，验收后已逐文件删除，目录也已移除。独立 Chromium 已关闭，未停止原有 Vite 服务，未写入真实用户数据。
