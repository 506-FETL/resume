## 四个可以分别验收的问题

1. 首页业务读取启动较晚。HTML 返回后，外壳先显示通用指示；首页、认证订阅、各卡片的数据 effect 随组件挂载而启动。6 个请求本身在 27 毫秒内并发发出，最后一项就绪到最终 LCP 还有约 354 毫秒。DevTools 的 1,456 毫秒“元素渲染延迟”包含这段客户端启动、业务取数和内容展示，不能作为绘制函数的 CPU 时间。可先验证在真实身份确认且选中首页时启动现有的在途请求，并保留账户隔离、局部重试和真实骨架。验收看真实标题、第一项可用待办及最终文本绘制。
2. 骨架切换时有两次无输入偏移。1.033 秒顶部操作区宽度变化贡献约 0.00012；1.258 秒下方两组内容上移贡献约 0.02040，本次合计约 0.02052。截图中岗位提醒正从两行骨架收成较矮的内容；这是上移原因的首要排查点。位移节点已确定，浏览器没有自动确定触发节点。最近简历列表另有一个可验证的等待：卡片接口 1.105 秒完成，真实卡片约 1.267 秒开始渲染，共用过渡默认先执行 140 毫秒退出。这两处应分别核对最终几何和真实内容首次可见时间，保留主动切换的动效。
3. 可见预览等待多层前端准备。卡片挂载后依次经历可见性观察、缩略图与缓存模块、effect、正文读取模块。真正开始取正文前已消耗约 0.68 秒，两份正文随后并发。现有实现已将正文与生成器并行准备，但请求的启动仍依赖前述挂载过程。优先验证由可见卡片直接启动轻量读取，保留可见性、真实模板、版本缓存和安全的正文渲染。DevTools 的网络链上限 2.30 秒与第二份正文完成时刻吻合；截图收起了具体条目。所有首页 REST 读取复用同一条 HTTP/2 连接，当前样本没有新的 DNS 或 TLS 握手需要预连接。
4. 图表和预览仍有主线程开销。漏斗和 ATS 图表在带 200 像素提前量的视口观察下挂载。1.590 秒的 122 毫秒任务包含图表与 React 提交；2.221 秒和 2.385 秒开始的两个任务约 58 和 55 毫秒，含简历模板生成、富文本处理与布局。两次生成附近另有 24 个字体资源，解码后约 1.28 MB，均晚于 LCP。59.6 毫秒处另有一个约 60 毫秒的长任务，来自扩展注入的脚本。用无扩展的生产构建、相同两份简历及相同视口复测，再决定是否错开临近视口图表的挂载或降低模板生成成本。分别记录两张预览可见时刻，不用浏览器 load 或网络链结束代替。

本轮只分析该次录制。它足以定位当前页面上已经观察到的等待和位移，生产环境的耗时与优化收益尚未由这份样本验证。
