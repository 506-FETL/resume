# AI 简历工具本地/云端边界修复设计

## 背景与根因

简历产品同时存在两种数据源：

- 云端简历：`resume_config.resume_id` 为 PostgreSQL `uuid`，通过 Supabase/PostgREST 读取。
- 本地简历：`resume_id` 为 `local-<uuid>`，正文和元信息保存在 IndexedDB。

编辑器已经按 ID 前缀区分两种数据源，但 AI 助手仍默认所有简历都来自 `resume_config`。因此当前简历为本地简历时，助手画布和 `get_resume_detail` 会把 `local-*` 传给 UUID 列，触发 `22P02/400`。普通简历页删除简历后也没有清理持久化的当前选择；画布随后用 `.single()` 查询已删除 UUID，合法的零行结果被 PostgREST 转成 `PGRST116/406`。

此外，`update_current_resume_field` 在云端读取失败后回退到编辑器内存。助手页通常没有加载编辑器文档，此时内存可能只是默认空表单，不能作为本地简历的真实修改基线。

## 目标

1. 本地简历 ID 永远不进入 Supabase UUID 查询。
2. AI 助手可以列出、读取、打开、修改正文、修改元信息和删除本地简历。
3. 云端简历不存在时不再产生 `PGRST116/406`，并清理失效的当前选择。
4. 修改正文始终以目标简历的真实持久化内容为基线，而不是未初始化的共享 store 默认值。
5. 历史版本、ATS 和派生血缘等云端专属能力对本地简历明确拒绝，不隐式上传、不返回数据库类型错误。
6. 保留现有写操作确认卡、Automerge 云端同步和 IndexedDB 本地同步行为。

## 方案比较

### 方案 A：助手禁用本地简历

在发现 `local-*` 时直接提示先同步到云端。改动最小，但用户已经能在产品中打开本地简历，助手却不能读取和修改，产品能力不一致。

### 方案 B：调用工具前自动上传本地简历

可把后续逻辑统一成云端 UUID，但会产生未经用户确认的数据迁移、ID 替换和本地记录删除风险，不符合本地模式的语义。

### 方案 C：统一可访问简历边界（采用）

新增轻量数据访问层，按 ID 类型路由 IndexedDB 或 Supabase。通用 AI 读写和画布使用该边界；真正依赖云端表关系的功能保留云端限定。该方案不改变数据库结构，也不迁移用户数据，能从根因上消除数据源混用。

## 设计

### 1. ID 与错误边界

- 提供共享 UUID 判定函数。
- Supabase 的 `getResumeById` 在发请求前拒绝非 UUID，确保 `local-*` 或任意畸形 ID 不会进入 `.eq('resume_id', ...)`。
- 查询改用 `.maybeSingle()`；零行时抛出可识别的 `ResumeNotFoundError`，而不是让 PostgREST 返回 406。

### 2. 统一可访问简历数据层

提供以下能力：

- 并发列出云端简历与 IndexedDB 本地简历，并标注 `isOffline`。
- 按 ID 读取：本地记录将元信息与 `data` 展平成与 `resume_config` 相同的读取形态；云端记录继续走现有 API。
- 按 ID 更新元信息和删除：分别路由 IndexedDB 或 Supabase。
- 提供本地简历/云端简历能力判定，供历史版本和派生功能使用。

该层只统一“简历本身”的 CRUD，不伪造本地历史版本、ATS、分享或派生血缘。

### 3. AI 工具

- `list_resumes` 返回本地与云端简历，并显式提供存储位置。
- `get_resume_detail` 使用统一读取，不再把本地 ID 送到 Supabase。
- `update_current_resume_field` 先读取目标简历的真实持久化模块作为合并基线，再沿用现有 schema 校验、确认卡和 `applyResumeFieldToDocument` 同步链。
- `update_resume_meta`、`delete_resume`、`open_resume` 使用统一读取/写入；`open_resume` 必须先验证目标存在，并以真实类型设置当前简历。
- 保存/恢复历史版本以及派生血缘在本地简历上返回明确的“请先同步到云端”提示。

### 4. 助手上下文与画布

- 用户上下文使用统一列表，避免模型只看见云端列表却同时收到一个本地 current ID。
- Composer 的 `@` 简历引用使用同一列表，使用户可以显式引用本地简历。
- 画布先完成可访问简历列表加载，再解析预览目标；本地目标直接从 IndexedDB 构建快照。
- 如果持久化的当前 ID 已不存在，清理当前选择；有其它简历时仅将画布预览切到第一份可用简历，没有时显示空状态。
- 列表请求失败与“没有简历”分开处理，避免网络故障误清理用户选择。

### 5. 删除后的选择一致性

普通简历页和 AI 删除工具在删除当前简历成功后都清理 `useCurrentResumeStore`。失败时不清理，保持现有乐观列表行为。

### 6. 编辑器打开门禁

自有云端简历在创建或载入 Automerge 文档前确认 `resume_config` 行仍然存在，避免已删除 UUID 被错误初始化为一份空白文档。共享 `documentUrl` 不执行所有权行门禁，因为协作者可能无法直接读取所有者的 `resume_config`；该路径继续以共享文档本身为准。编辑器确认目标不存在后清理持久化 current ID 并返回简历列表。

## 错误处理

- 非 UUID 云端读取：客户端直接抛出明确错误，不产生 HTTP 请求。
- 合法 UUID 零行：抛出 `ResumeNotFoundError`；画布可据此自愈，其他调用点显示“简历不存在或无权访问”。
- IndexedDB 找不到本地记录：同样归一为目标不存在。
- 数据源临时失败：保留当前选择并显示加载失败，不当作记录已删除。
- 本地简历调用云端专属功能：返回能力边界提示，不触发 Supabase 请求。

## 验证范围

1. 静态专项验证：断言 Supabase 单行读取使用 `.maybeSingle()` 且有 UUID 前置校验；AI/画布改用统一数据源；本地历史/派生有能力门禁。
2. 目标文件 ESLint 与 TypeScript/构建验证。
3. `git diff --check` 与调用点复扫。
4. 使用当前已链接 Supabase 项目执行只读 smoke：合法但不存在的 UUID 应返回空集合语义，不再依赖 406；不做数据库迁移或 Edge Function 部署，因为本修复仅修改客户端。
5. 浏览器验收重点：本地简历画布、读取工具、修改确认后刷新持久化；删除当前简历后助手不再查询旧 ID；云端简历正常读写不回归。

## 非目标

- 不自动把本地简历上传云端。
- 不为本地简历新增历史版本、ATS、分享、评论或派生血缘的离线实现。
- 不改变 Supabase schema、RLS 或 Edge Functions。
