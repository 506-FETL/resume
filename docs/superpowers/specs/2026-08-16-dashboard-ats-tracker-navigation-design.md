# 首页 ATS 趋势与求职看板指标导航设计

## 背景

首页“ATS 分数趋势”目前始终只有旧日期，原因有两层：同一份简历重新检测时会覆盖已有 `ats` 行，而且首页又按简历去重，只保留每份简历最近一条。覆盖不会更新 `created_at`，因此重复检测既不会形成历史点，也会继续显示首次创建时间。

求职跟进的顶部指标在列表视图和看板视图共用了 `metricFilter`。列表视图需要过滤数据；看板视图则应保留所有列和卡片，只把用户导航到目标列。当前看板错误地把指标传给 `filterJobs`，导致无关卡片被隐藏。

## 目标

- 每次成功完成 ATS 检测都形成一条不可变的检测记录。
- 优化页始终把指定简历最新一条记录当作当前报告。
- 首页趋势展示所有在线简历最近 8 次有效检测，而不是每份简历一个点。
- 看板指标点击后只滚动并高亮目标列，不过滤卡片。
- 列表视图继续保留指标筛选行为。
- 桌面端和移动端使用相同的导航与高亮语义。

## 非目标

- 不恢复已经被覆盖的历史 ATS 检测；数据库中不存在的数据无法可靠重建。
- 不改变 ATS 报告修复清单、格式化工具等对“当前报告”的更新方式。
- 不改变求职指标的统计口径。
- 不改变看板拖拽、归档或搜索行为。

## ATS 数据设计

### 写入

`startAnalysis` 在模型结果校验、归一化完成后始终调用 `createAtsConfig`。不再按 `resume_id` 查找旧行并覆盖。成功提示统一为“ATS 分析报告已生成”。

### 当前报告读取

`getAtsFromUserId` 按 `created_at DESC, id DESC` 返回，保证同一秒内的记录也有稳定顺序。优化页继续通过 `find(resume_id)` 选取报告，因此自然得到该简历最新一条。为避免历史行扩散到依赖“每份简历一条”的选择器，初始化时将查询结果归一化为每个 `resume_id` 的第一条记录，再写入 `atsConfigs`。

### 首页趋势

`listAtsSummaries` 保留全部记录。趋势处理只过滤在线简历和有效数值分数，按 `created_at`、`id` 正序稳定排序后取末尾 8 条。图表标题不变，说明改为“最近 8 次检测得分”。

首页平均 ATS 分与待修复项仍按每份简历最新报告计算，避免拥有更多历史检测的简历获得更高权重。

## 看板导航设计

### 指标到列的映射

- `applied` → `applied`
- `interview` → `interview`
- `offer` → `offer`
- `pending` → 最紧急待跟进职位当前所在列

“待跟进”的候选集合继续使用 `isJobPendingFollowUp`。有 `next_action_date` 的候选按日期从早到晚排序；无明确日期的候选排在有日期候选之后，并按 `updated_at` 从早到晚排序。首个候选的当前 `status` 是目标列。没有候选时不滚动、不高亮列，但指标可以保持无选中状态。

### 视图语义

`metricFilter` 仍记录当前指标：

- 列表视图把它传给 `filterJobs`。
- 看板视图只把它解析为目标列，调用现有平滑滚动能力，构建列数据时向 `filterJobs` 传 `null`。

`filterStatus` 的既有列导航能力保留。看板列高亮目标按 `filterStatus` 优先，否则使用指标目标列。点击同一个指标再次取消后清除高亮。

批量选择在看板视图按实际可见的全部看板卡片执行，不得因为 `metricFilter` 仍有值而只选择指标集合；列表视图继续按指标筛选后的结果执行。

### 视觉与动态效果

目标列沿用现有列头、计数徽标和投放区域的整体高亮，不新增嵌套卡片。滚动使用 `smooth`；当用户启用减少动态效果时使用即时滚动。列已完全可见时不强制移动，只更新高亮。

## 错误与边界处理

- ATS 写入失败时不覆盖旧报告，沿用现有错误提示。
- 同一简历连续检测生成多行是预期行为。
- 搜索关键词仍可让目标列显示为空；导航基于完整求职指标，不篡改搜索条件。
- 待跟进职位在点击后被更新时，下一次点击重新计算目标列。

## 验证

- 验证连续两次 ATS 检测调用两次插入，并且优化页仍选择最新报告。
- 验证趋势按时间取最后 8 条，不再按简历去重。
- 验证列表视图四个指标继续过滤。
- 验证看板视图四个指标不改变卡片总数，分别定位并高亮正确列。
- 验证“待跟进”在明确日期与陈旧记录混合时选择规则稳定。
- 验证移动端横向看板和桌面端行为一致。
