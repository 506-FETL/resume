# 历史版本模块：产品锐评与彻底优化建议

- 日期：2026-08-10
- 范围：`/history` 页面、简历编辑器工具栏「历史版本」下拉、AI 助手画布「历史版本 / 变更记录」
- 数据源：Supabase 表 `resume_config_versions`（全量 JSON 快照）
- 结论定位：**功能不少，但被拆成三套重复 UI；同时缺了版本历史真正的核心价值——「对比」和「针对岗位的版本管理」。**

> 本文只做调研 + 锐评 + 优化建议，不改代码。落地时另开 spec/plan。

---

## 一、现状盘点（代码事实）

三套 UI 读写**同一张表**，各自重复实现列表、预览、动画、恢复逻辑：

| 界面 | 位置 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| 完整历史页 | `src/pages/history/**`（`/history`） | 切简历、保存版本（名称/里程碑/描述/标签）、看结构化内容、看渲染简历、改元信息、恢复、删除 | 无对比、无搜索/筛选、无导出、无分页 |
| 编辑器工具栏下拉 | `src/pages/resume/editor/components/toolbar/history-version-dropdown.tsx` | 列表、回滚、预览 | 元信息编辑、删除、标签、内容视图都没有——是历史页的子集 |
| 助手画布「历史版本」 | `src/pages/assistant/components/assistant-canvas/version-timeline/index.tsx` | 只读迷你时间线（V号+日期+里程碑） | 无任何操作 |
| 助手画布「变更记录」 | `.../change-log/index.tsx` | 本轮 AI 逐字段红绿 diff + 单条撤销 | 与版本表无关，是另一个概念 |

版本记录字段（`src/lib/supabase/resume/history/types.ts:14-33`）：`version_no / version_name / description / milestone_name / source_type / tags / snapshot / content_hash / base_updated_at`。

版本创建路径（均走 `createResumeHistoryVersion`）：
- 手动保存（历史页 / AI `save_current_resume_version` 工具）→ `source_type: 'manual'`
- 恢复副作用（`restore.ts`）→ 一条 `autosave`「恢复前备份」+ 一条 `restore`

## 二、市场调研：主流产品怎么做版本/多版本

调研 Teal、Huntr、Rezi、Enhancv 及「简历版本管理」最佳实践，几条清晰信号：

1. **「多版本」的真实场景是「一岗一版」，不是「时间线备份」。** 用户核心诉求是：一份基线简历 → 针对不同岗位/公司派生命名清晰的变体（如 “前端-字节”“后端-某厂”），并记录**投了哪一版、结果如何**（profileops、resumly 的 ChangeLog 实践）。这正是求职场景下版本管理的价值所在。
2. **Rezi / Huntr / Teal 的重心是「Job Tailoring（按岗定制）+ 定制报告」**，把「版本」和「投递的岗位」强绑定，而不是给你一条 Git 式的自动备份流水。
3. **Teal 的差异化亮点是「逐条 bullet 的关键词级控制」**，尤其适合在两个职业身份之间切换的用户——即**细粒度对比与取舍**，而非整份快照回滚。
4. 通用最佳实践反复强调：**清晰命名 + 日期 + 记录改了什么 + 记录投了哪一版**，目的是「避免投错文件、加速定制、复盘哪一版更容易过筛」。

**对照结论：** 本产品已经有独立的「JD 驱动派生简历」能力（`src/components/jd-variant`）——这才是对标市场的核心资产。而「历史版本」目前做成了一条**通用时间线备份**，与派生体系割裂，既没吃到「一岗一版」的场景红利，又把力气花在了三套重复 UI 上。

## 三、锐评：哪些是重复/没必要的，可以砍

1. **三套版本列表 UI 属于重复建设。** 编辑器工具栏下拉几乎是历史页的残缺子集，助手画布迷你时间线只读且信息量极低。→ **建议砍掉「工具栏下拉」和「画布只读时间线」两处独立实现**，统一入口到 `/history`，工具栏只保留一个「打开历史版本」跳转 + 「快速保存当前版本」。
2. **两个近乎相同的只读预览弹窗**：`history/components/preview-dialog` 与 `toolbar/version-compare.tsx`（后者名字叫 compare 却根本不做对比，误导）。→ **合并为一个**，并给它补上真正的「对比」。
3. **死代码 / 名不副实**：
   - `source_type` 的 `ai_optimize`、`import` 从未被写入（`Grep` 全仓无写入点），但 `SOURCE_META` 和首页信息流（`insights.ts:268`）还在为它们分支。→ 要么接上真实写入，要么删掉分支。
   - `version-compare.tsx` 命名误导，应改名或直接并入统一预览。
4. **重复工具函数**：`snapshot.ts:createResumeSnapshotHash` 与 `history/utils.ts:createSnapshotHash` 是同一套哈希实现两遍。→ 合一。
5. **重复的恢复编排**：历史页 store 和工具栏下拉各写一遍 `restoreResumeHistoryVersion` + toast + reload。→ 抽成一个 `useRestoreVersion` hook。
6. **`content_hash` 存了却从不用**：既不去重、也不驱动「有无未保存改动」的判断复用。→ 要么用起来（见下「去重」），要么别存。

## 四、锐评：缺了什么关键能力

按「痛点 → 缺失」排列，越靠前越致命：

1. **没有版本对比（最致命）。** 版本历史的头号价值就是「看两版差在哪」。仓库里明明已有成熟的行级红绿 diff（`DiffView` + `compute-line-diff.ts`），却**只接在助手的本轮变更记录上**，没接到版本记录。用户无法回答「这版比上一版改了什么」「A 版和 B 版哪个更贴岗位」。
2. **与「岗位/派生」体系脱节。** 已有 JD 派生，但历史版本不知道「这一版是投给哪个岗位的」，也无法从某个版本一键「派生新变体」或「标记为已投递给 X」。这正是市场公认的核心场景，却是当前最大缺口。
3. **保存全靠手动，且会存重复。** 没有任何自动快照节奏（`autosave` 只在恢复时产生），关键节点容易漏存；同时 `content_hash` 不去重，连点两次「保存」会产生两条一模一样的版本。
4. **无搜索 / 筛选 / 排序。** 标签（tags）采集了却无处可筛（`tag-input` 注释写着「方便后续查找」，但根本没有查找）。版本一多，时间线就是一堵墙。
5. **无分页 / 虚拟化 + 无保留上限。** `listResumeHistoryVersions` 一次拉全量、全量渲染，且永不清理，长期必然膨胀与卡顿。
6. **无导出。** 不能把某个历史版本单独导出/下载 PDF——而「投出去的那一版」恰恰是最该能取回的。
7. **本地（offline）简历完全不支持历史。** 只对云端简历可用。
8. **恢复不可逆感知弱。** 虽然恢复前会自动备份，但用户对「恢复=覆盖当前」这件事的心智提示较弱。

## 五、彻底优化建议（分层，按 ROI 排序）

### P0 — 立刻做，解锁核心价值
1. **版本对比视图**：复用 `DiffView`/`compute-line-diff.ts`，在历史页详情面板加「与上一版对比 / 选任意两版对比」。这是把「备份流水」升级成「版本历史」的关键一步。
2. **保存去重**：保存前用 `content_hash` 比对最近一版，内容相同则提示「与最新版本一致，无需保存」，不再产生重复行。

### P1 — 收敛重复，降低维护成本
3. **三套 UI 收敛为一**：`/history` 为唯一完整体验；工具栏只留「打开历史 + 快速保存」；助手画布只读时间线改为跳转 `/history`。删除 `version-compare.tsx` 的重复预览，合并预览弹窗。
4. **抽公共 hook**：`useRestoreVersion`、统一 `createSnapshotHash`、统一 `SOURCE_META`。
5. **清死代码**：接上或删除 `ai_optimize`/`import` 分支（建议：让 AI 优化保存的版本真正写 `ai_optimize`，首页信息流才名副其实）。

### P2 — 对齐市场，做深场景
6. **版本 ↔ 岗位打通**：版本记录可关联一个「目标岗位/派生来源」；支持从版本一键「派生新变体」；支持标注「已投递给 X（日期）」，呼应市场公认的「一岗一版 + 记录投了哪版」。
7. **搜索/筛选/排序**：按名称、标签、来源、里程碑、日期范围过滤，让 tags 真正可用。
8. **分页 / 虚拟化 + 保留策略**：分页加载；提供「保留最近 N 版 + 里程碑版永久保留」的清理策略，里程碑版受保护不被清。

### P3 — 锦上添花
9. **单版本导出 PDF**；恢复二次确认强化「覆盖当前」的心智；（可选）本地简历的轻量历史支持。

---

## 六、一句话总结

> 当前「历史版本」是**一条被复制了三遍的通用备份流水**；市场对标产品的价值锚点是**「按岗位的多版本管理 + 版本对比」**。优先补上「对比」和「与派生/岗位打通」，同时把三套重复 UI 收敛成一套，就能用更少的代码换来明显更高的产品价值。
