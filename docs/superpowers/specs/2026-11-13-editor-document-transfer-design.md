# 简历打开正文传输优化

日期：2026-11-13。用户授权排查完整链路，并按推荐方案落地。当前分支实施，不推送；实施、验证、用户审查分别记录。

## 实测根因

在用户本机 Chrome、5173 开发服务、真实“全栈开发”上，两次已有文档打开分别记录正文 GET 23,939 ms / 17,295 ms；其中响应头后的正文传输约 19.6 s / 14.9 s。解码加 Automerge 导入为 330 ms / 225 ms，导入后约 100–140 ms 出现纸张正文。两次外观请求与正文请求已并行，WASM 没有挡住 GET。评论在正文出现后加载，实际执行区域为 us-east-1。

该文档原始二进制 138,275 B，持久化列保存 Base64 的 ASCII 字节共 184,368 B，PostgREST 对 bytea 输出十六进制，单字段 JSON 值扩大为 368,741 B。SQL 查找实测 2.369 ms；数据库仍在 us-east-1，健康检查无告警。文档更新时间为 11 月 5 日，因此没有证据证明最近修改造成数据增长。本次确认的是慢公网传输叠加长期存在的重复编码；不能把网络波动说成前端 CPU 回归。

## 推荐方案与取舍

新增只读、调用者权限的 get_automerge_snapshot RPC，返回与现有解码器兼容的 Base64 文本。当前 ASCII Base64 bytea 直接转回文本；原生 Automerge bytea 按魔数识别后编码为 Base64。保留 null / 不存在 / 请求失败 / 损坏文档的区别，不进行存储重写、CRDT 历史压缩或缓存正文。

此方案可将当前样本未压缩 JSON 正文减少约 50%，减少客户端十六进制转换。只在读取入口替换原单目标请求，继续通过 GET RPC 使用现有 Supabase SDK 的认证、刷新、临时错误自动重试和错误机制，外观并发、保存队列、账户代次、缺配置零写入、guest bootstrap、离线路径及模板预取不变。

其他方案：增加正文缓存会引入新鲜度与失效边界；迁移为原始二进制存储及自定义二进制下载会扩大旧客户端、协作与持久化兼容面。本次不采用。公网本身的延迟仍可能存在，不承诺固定打开秒数。

## 权限与兼容

函数为 STABLE、SECURITY INVOKER、空 search_path；按 resume_id 与传入 user_id 筛选，继续经过现有 automerge_documents 的 owner RLS（含 resume_config 归属复查）。只授予 authenticated 执行权，撤销 PUBLIC / anon 默认权限。不更改表权限、RLS、写入、Edge Functions 或真实简历数据。

原生魔数为 85 6f 4a 83。非原生内容按既有 ASCII Base64 存储协议转换；非法 UTF-8 或损坏 Base64 仍失败，不能降级为新建或回填配置正文。原有直接表读取继续供旧客户端使用；部署新函数后再切前端。

## 验收

使用真实 PostgreSQL 与正式函数验证两种编码逐字节一致、本人可读、跨账户/伪造 owner/匿名拒绝、缺失为空、损坏报错、无写入。用真实前端模块验证调用协议、失败与 null、保存后重开、guest 与离线不走新接口、账户切换与旧保存顺序不变。合成数据写入只在隔离环境进行。

部署当前 linked Supabase 项目，核对本地/远端迁移账本、函数定义与权限、Edge 版本保持，以及真实浏览器读取成功。交替记录旧/新读取和实际正文出现，区分网络波动与确定的字节变化；完整测试后删除 tests/editor-opening 下临时材料和诊断埋点，保留非敏感汇总。

执行类型检查、定向 lint、Prettier + ESLint layout、生产构建与全项目 format:check。UI 与动画不变；保留正文、编辑和真实保存验收，不以骨架出现作为完成。
