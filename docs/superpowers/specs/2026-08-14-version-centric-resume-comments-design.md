# 版本中心化简历全文评论深度优化设计规格

- 日期：2026-08-14
- 主题：version-centric-resume-comments
- 状态：已完成头脑风暴并获用户批准
- 范围：在线简历编辑器、历史版本、公开分享、全文划词评论、实时同步、移动端与桌面端评论界面
- 取代范围：本规格取代 `2026-08-13-resume-full-text-comments-design.md` 中“工作区 / 历史版本 / 分享发布批次分别隔离评论”“分享链接之间评论不互通”“回复仅允许一层”“右下角全局评论按钮”“移动端 snap points”等结论；未被本规格修改的安全、锚点和文本选择约束继续有效

## 1. 背景与问题

现有全文评论功能已经具备划词锚点、评论线程、匿名访问、编辑器与分享页接入、Realtime 和多种来源审阅，但当前领域边界以 `working/history/share_release` 三类评论空间组织。这个模型与真实产品目的冲突：用户分享某个版本，是为了让他人直接评论这个版本；用户继续编辑同一版本时，应实时看到分享访客的评论，分享访客也应在云端同步成功后看到最新正文。

当前实现同时存在下列问题：

1. 编辑侧栏打开后，固定在右下角的评论入口遮挡表单控件。
2. 评论来源把工作区、历史版本和分享发布混为不同来源，且任一来源请求失败都会显示笼统的“评论来源加载失败”。
3. 评论加载和写入经过多段串行同步、重复全量拉取与 Realtime 重复刷新，存在结构性延迟。
4. 关闭评论详情后，正文仍保留强高亮。
5. 回复没有清晰的递归树状关系，窄 Drawer 中层级容易挤压内容。
6. 主题卡片缺少快捷解决入口。
7. 移动端将 Drawer 的 `snapPoint` 从非受控切换为受控，出现 Base UI 警告，首次打开高度异常。
8. 分享页移动端首次渲染可能按桌面状态从右侧打开 Drawer。
9. 编辑器和分享页即使展示的是同一个版本，也因评论空间不同而看不到同一组评论。
10. 评论入口不符合飞书式贴边书签形态。
11. 发送、回复、编辑、删除、解决、来源切换和权限刷新缺少完整的进行中、成功校准与失败回滚反馈。

本次不是表面 UI 修补，而是把评论领域改成以稳定 `version_id` 为唯一内容与评论边界，同时治理真实请求链、实时增量、缓存、移动端 Drawer 和交互动效。

## 2. 目标与成功标准

### 2.1 产品目标

- 同一版本的编辑器、所有分享链接和所有合法访问者看到同一份正文与同一组评论。
- 当前活动版本在成功同步云端后更新正文；手动创建新版本后，旧版本冻结，新版本内容相同但评论为空。
- 桌面端使用贴在预览区域右上边缘的飞书式评论书签和右侧 Drawer。
- 移动端编辑页、分享页统一使用从底部进入、无 snap points 的有界自适应 Drawer。
- 回复支持任意递归深度，但 UI 在窄容器中保持可读。
- 所有异步动作具有就地进度、乐观反馈、失败回滚和合理动画；正常成功不使用 Toast。
- 用分段耗时和请求数量证明性能瓶颈被消除，而不是只用 Skeleton 掩盖等待。

### 2.2 性能目标

- 有可用缓存时，打开 Drawer 后首批评论目标在 100ms 内出现。
- 无缓存冷加载目标不超过 2s。
- 发送、回复、解决、编辑和删除的本地反馈目标在 100ms 左右出现。
- 正常一次写操作只有一次 mutation 请求，不紧跟全量 `list_threads`。
- 正常一次 Drawer 冷启动只有一次 bootstrap；版本来源独立加载，不阻塞当前评论。
- Realtime 对自己已乐观处理的事件去重，不因同一动作再次全量 bootstrap。

### 2.3 非目标

- 离线简历评论及离线转在线时的评论迁移。
- 评论附件、图片、富文本格式、@ 提及、点赞、表情、翻译和举报。
- 将评论或高亮写入简历快照、PDF、打印或 Tiptap 文档。
- 通过内容哈希在运行时推断“是否同一版本”。
- 本次直接删除旧评论空间、旧分享发布字段或旧审计数据。

## 3. 核心领域决策

### 3.1 版本是唯一边界

所有正文、评论、分享链接、锚点文档、未读游标和 Realtime 事件统一归属稳定的 `version_id`。`working/history/share_release` 不再是长期运行时的评论隔离语义。

同一个 `version_id`：

- 只有一个权威正文快照；
- 只有一个权威评论空间；
- 可以被多个分享链接引用；
- 编辑器与分享页订阅同一个评论事件序列；
- 不通过 `resume_id`、内容哈希或分享发布 ID 猜测评论归属。

### 3.2 活动版本与冻结版本

版本状态只有：

- `active`：当前工作版本。版本 ID 稳定，正文仅在云端同步成功后更新。
- `frozen`：已冻结版本。正文不可修改，评论仍可继续查看、回复和管理。

每份在线简历同一时间只能有一个 `active` 版本。离线简历没有评论版本空间。

### 3.3 创建新版本

用户主动创建新版本时，由数据库事务完成：

1. 锁定简历及当前活动版本；
2. 将旧版本状态改为 `frozen`；
3. 复制旧版本快照、模板信息和投影基准，创建新的 `active` 版本；
4. 为新版本创建空评论空间和初始锚点文档；
5. 更新 `resume_config.current_version_id`；
6. 原有分享链接继续指向旧版本；
7. 编辑器切换到新版本。

新版本不复制旧评论、未读游标或解决状态。

### 3.4 分享链接

`resume_shares.version_id` 是分享内容和评论的权威版本引用。多个链接可以指向同一版本：

- 所有链接看到相同正文与评论；
- 每个链接仍独立控制密码、有效期、启用状态、评论开关和访问统计；
- 某个链接关闭评论只会让通过该链接进入的访客变为只读，不改变版本评论空间；
- 某个链接失效不会删除版本或评论；
- 创建新版本不会自动移动旧链接。

`resume_share_releases` 暂时保留作为兼容与审计数据，但不再作为评论隔离边界，也不再作为绑定活动版本链接的正文真源。

## 4. 数据模型

### 4.1 resume_config_versions

在现有版本表上增加或统一：

- `status text not null check (status in ('active', 'frozen'))`；
- `document_revision bigint not null default 1`；
- `projection_reference_date date not null`；
- 继续使用现有 `snapshot`、`content_hash`、`version_no`、`version_name` 和创建时间字段。

数据库部分唯一索引保证每个 `resume_id` 最多一个 `active` 版本。活动版本成功同步后更新 `snapshot/content_hash/document_revision`；冻结版本拒绝正文更新。

### 4.2 resume_config

增加：

- `current_version_id bigint null references resume_config_versions(id)`。

在线简历必须指向属于自己的活动版本；离线简历保持为空。

### 4.3 resume_shares

增加：

- `version_id bigint null references resume_config_versions(id)`。

有效在线分享必须绑定版本。读取分享时，服务端先校验链接权限，再由 `version_id` 读取权威版本快照。

### 4.4 resume_comment_scopes

增加：

- `version_id bigint null references resume_config_versions(id)`；
- 对非归档版本空间建立 `version_id` 唯一约束。

迁移完成后，每个版本只有一个权威评论空间。旧 `kind/history_version_id/share_release_id/resume_id` 字段暂时保留，供兼容读取、审计和迁移回滚使用。

### 4.5 递归回复

`resume_comments.parent_id` 可以指向同一线程中的任意未物理删除评论，不再要求只能指向主评论。服务端校验：

- 父评论与子评论属于同一线程和版本；
- 不能指向自己；
- 不能形成环；
- 根评论仍由 `parent_id is null` 唯一确定；
- API 和 UI 不设置业务深度上限。

删除存在后代的评论时保留 tombstone，正文为“该评论已删除”，后代和树关系继续存在。删除没有后代的非根回复可以软删除并在展示树中隐藏；审计数据保留。

### 4.6 版本事件序列

评论事件以版本评论空间为边界维护单调递增的 `event_seq`。事件至少包含：

- `event_id`；
- `event_seq`；
- `version_id`；
- `thread_id/comment_id`；
- 动作类型；
- 必要的已清洗增量实体；
- actor 摘要；
- 创建时间。

客户端使用 `event_id/event_seq` 去重、补偿断档和维护未读。

## 5. 正文同步与锚点

### 5.1 成功同步才更新分享正文

本地表单编辑只更新本地工作状态。云端保存成功后，统一同步入口原子地：

1. 更新简历云端配置；
2. 更新活动版本快照和 `document_revision`；
3. 更新版本评论空间的权威 `anchor_document`；
4. 对未解决锚点执行确定性重定位；
5. 生成版本正文更新和锚点状态事件。

任一步失败时，分享页继续显示上一次完整成功的版本快照，不对外暴露半同步状态。

### 5.2 已发布评论重定位

正文更新后：

- 优先使用 node key、原文、前后文、字素偏移和语义块信息重新锚定；
- 可靠匹配成功后更新锚点，继续显示弱高亮；
- 无法可靠定位时改为 `detached`，进入“失去锚点”；
- 不因正文变化删除评论；
- 重定位在服务端使用统一纯函数完成，浏览器只消费结果。

### 5.3 未发送草稿冲突

分享访客已选中文字并输入草稿时收到新正文：

- 立即展示新正文；
- 保留草稿；
- 清除旧选区和旧锚点；
- 就地提示“简历内容已更新，请重新选择文字后发送”；
- 提交请求携带 `base_document_revision`；
- 服务端发现 revision 过期时返回结构化冲突，客户端保留草稿并要求重新选择。

## 6. 评论 API 与性能治理

### 6.1 已确认的结构性慢因

当前一次评论写入可能串行等待：简历手动同步、工作文档同步、身份准备、Edge Function 权限解析、完整简历读取、作用域确保、数据库写入、广播、显式全量刷新以及同一广播触发的再次全量刷新。Bootstrap 还存在来源加载耦合、作者资料补查和顺序作用域查询。

### 6.2 访问解析

评论 API 直接通过已校验的 `version_id` 解析权威评论空间：

- 不在每次评论请求中重新读取完整简历；
- 不在每次评论请求中重复创建或同步作用域；
- 锚点文档只在正文成功同步时更新；
- 当前登录会话和短期访问令牌在安全期限内复用；
- 仍在每次写入时验证角色、版本归属和链接能力。

### 6.3 Bootstrap

一个 bootstrap 返回：

- 版本元数据和文档 revision；
- 当前访问权限；
- 未解决、已解决和失去锚点计数；
- 当前页评论线程和递归评论实体；
- 批量作者资料；
- 当前 event seq 与 Realtime 连接信息。

作者资料通过批量 join/RPC 返回，避免评论列表加载后逐个补查。长列表支持游标分页，但首屏必须返回完整可展示线程结构。

### 6.4 Mutation

创建、回复、编辑、删除、解决、重新打开和重新关联均返回：

- 变更后的标准化实体或 tombstone；
- 更新后的主题计数；
- `event_id/event_seq`；
- 最新 revision；
- `request_id`。

客户端先做乐观更新，再用响应校准；正常成功后不调用全量 `refreshThreads`。只有事件断档、revision 冲突或本地校验失败时才后台重建。

### 6.5 Realtime

- 自己已乐观应用的 `event_id` 不重复处理；
- 其他客户端的事件增量合并；
- event seq 连续时不全量刷新；
- event seq 断档时只补拉缺失事件，无法补偿才 bootstrap；
- 权限心跳只续期权限和 Realtime 凭证，不重新下载完整评论；
- 广播发送不作为数据库事务成功的必要条件，写入响应不因广播延迟长期阻塞。

### 6.6 来源加载错误

来源选择器只展示版本，不再展示分享发布批次。当前版本立即可用，历史版本独立加载：

- 不使用一个 `Promise.all` 让任一子请求拖垮全部来源；
- 保留 Supabase/Edge Function 的 `code/message/details/request_id`；
- 非标准 `Error` 对象也要规范化；
- 失败在来源区域就地展示并提供重试；
- 来源失败不影响当前版本评论；
- 每个版本可显示“已通过 N 个链接分享”。

## 7. 客户端缓存与状态

### 7.1 缓存边界

缓存键至少包含：

- `version_id`；
- principal 类型与稳定身份摘要；
- 访问能力指纹；
- 数据 schema 版本。

匿名缓存不存储原始分享 token 或匿名 secret。退出登录、权限撤销、分享失效或 schema 升级时清理对应缓存。

### 7.2 stale-while-revalidate

- 有缓存：立即展示最后一次成功数据，顶部显示轻量“正在同步”；
- 无缓存：显示结构化 Skeleton；
- 刷新成功：按实体和 event seq 无闪烁合并；
- 刷新失败：保留旧数据，显示“当前展示的评论可能不是最新内容”；
- 切换版本：保留旧版本视图直到新版本首屏准备完成，同时明确加载中的目标版本。

### 7.3 状态归属

评论 pending、错误、缓存、选中主题、活动高亮、草稿和来源加载状态进入评论领域 store/provider，避免每个 action hook 各自持有不一致的 pending 状态。页面级 UI 状态保留在页面 store，本地输入框文本保留在组件局部状态。

## 8. 桌面端交互

### 8.1 飞书式贴边书签

评论入口固定在简历预览可视区域右上边缘：

- 采用贴边书签形态，不是右下角浮动按钮；
- 左侧露出圆角按钮和消息气泡图标，右侧与预览边缘贴合并部分收进边界；
- Hover 使用项目 shadcn Tooltip，文案“展开评论”；
- Hover 轻微向左露出并增强阴影，按下轻微缩放；
- Drawer 打开时图标平滑切换为激活色；
- 不使用持续弹跳、呼吸或干扰阅读的动画。

编辑侧栏打开时，书签停靠在预览区与编辑侧栏交界处，不覆盖表单。点击书签先收起编辑侧栏，再打开评论 Drawer；关闭评论后不强制恢复编辑侧栏。

离线简历不挂载评论 Provider，不请求作用域或 Realtime，也不展示可交互评论入口。

### 8.2 桌面 Drawer

- 使用现有 Base UI `Drawer`，从右侧进入；
- 宽度受视口约束，目标约 400px，窄桌面不溢出；
- 头部、版本来源和输入区固定，中间评论区滚动；
- 打开 Drawer 不改变简历预览布局宽度，避免正文重排和锚点漂移；
- 点击正文高亮可以切换当前主题；
- Esc 先关闭临时菜单/编辑态，再关闭主题详情，最后关闭 Drawer。

## 9. 移动端交互

### 9.1 统一底部 Drawer

编辑页和分享页复用同一移动端判定和评论展示组件，始终从底部打开。删除评论 Drawer 的全部 `snapPoints/snapPoint/onSnapPointChange` 状态，消除受控与非受控切换。

### 9.2 固定高度与内容滚动

- Drawer 固定为 `60vh`，列表、空状态与详情切换不改变外层高度；
- 头部、筛选栏和输入区固定，中间区域独立滚动；
- 使用 Base UI `Drawer.VirtualKeyboardProvider` 协调软键盘；
- 处理 `safe-area-inset-bottom`、横屏和极矮视口；
- 键盘弹出后输入框与发送按钮保持可见。

## 10. 高亮与正文反馈

- 未解决且未激活：弱暖色背景与轻量下边线；
- Hover 对应评论、点击锚点或当前详情：强高亮；
- 关闭详情或 Drawer 后约 160ms 退回弱高亮；
- 已解决和 detached 默认不绘制正文高亮；
- 高亮只动画背景、描边和透明度，不缩放文字或改变正文布局；
- 重叠锚点继续提供目标线程选择。

## 11. 递归回复 UI

### 11.1 树状布局

- 浅层回复使用轻量竖线和短横线展示父子关系；
- 缩进有 UI 上限，但数据递归无上限；
- 容器不足时显示“继续查看 N 条回复”；
- 点击进入“回复详情”，在完整宽度中重置缩进；
- 不出现“深层”“层级”“第几级”等技术词；
- 每条评论均可回复，输入区显示“回复 @用户名”。

### 11.2 快捷回复

- 使用消息/信息气泡图标，不使用折返箭头；
- 桌面端 Hover 或键盘聚焦时在每条评论下显示；
- 移动端始终显示；
- shadcn Tooltip 使用“回复 seams”一类用户化文案；
- 操作必须能键盘聚焦并有明确 aria-label。

## 12. 快捷解决与异步反馈

### 12.1 快捷解决

主题卡片右下角排列为 `[解决图标] [N 条回复]`。只有具备权限的用户看到解决按钮。

- 点击后乐观移出“未解决”；
- 图标原位切换为旋转状态并防止重复点击；
- 成功静默完成，不显示 Toast，不提供撤销；
- 失败回滚到原位置并显示卡片内错误。

### 12.2 全操作反馈

- 发送：旋转图标 + “发送中”；
- 回复：旋转图标 + “回复中”；
- 编辑：原位显示“保存中”；
- 删除：保留卡片，操作区显示处理中；
- 解决/重新打开：图标原位处理；
- 来源切换：触发器内显示加载，旧内容保持；
- 权限校验和 Realtime 重连：Drawer 顶部轻量状态条；
- 失败保留草稿，在动作附近显示；
- 正常成功均不显示 Toast。

跨区域的正文同步失败、分享权限失效使用顶部状态条；单项动作错误只在对应卡片或输入区就地展示。

## 13. Motion 动画规范

项目已有 `motion/react`，本功能沿用现有节奏与缓动：普通内容约 0.18–0.22s，常用缓动 `[0.22, 1, 0.36, 1]`，列表使用 `AnimatePresence`、`mode="popLayout"` 和 `layout`。

### 13.1 Drawer

Drawer 外壳保留 Base UI 手势驱动的 transform 和遮罩动画，不额外用 Motion 竞争同一 transform。Motion 负责 Drawer 内部列表和状态变化。首次与后续打开使用同一轨迹。

### 13.2 新增与展开

- 新评论从 `opacity: 0, y: 6px` 在约 180ms 内进入；
- 新内容背景短暂弱强调，约 600ms 退回；
- 只动画新增节点，不重播全列表；
- 回复展开使用局部高度、透明度和轻微位移；
- 进入回复详情使用短距离横向过渡。

### 13.3 删除

- 无后代：内容淡出、高度收起、后续节点通过 layout 补位；
- 有后代：正文与“该评论已删除”交叉淡入淡出，卡片和树线保持；
- 请求进行中不提前移除；失败不播放退出动画。

### 13.4 解决、来源与状态

- 解决成功后卡片轻微向右并淡出未解决列表，其他卡片 layout 补位；
- 发送按钮文字和 Spinner 使用 `AnimatePresence mode="wait"`；
- 来源、空状态、Skeleton 和列表交叉淡入但保持容器高度稳定；
- 错误提示平滑展开与收起；
- 数量使用已有数字过渡能力。

### 13.5 性能与无障碍

- 建立统一 `COMMENT_MOTION` 常量；
- 优先动画 transform/opacity，只在局部折叠时动画高度；
- 长树不对整个列表做 layout 动画；
- 稳定 key，防止 Realtime 更新重播进入动画；
- 使用 `useReducedMotion`：关闭位移、缩放和高度补间，只保留必要的即时状态或短淡入；
- 不为展示动画人为延迟真实请求完成。

## 14. 权限与安全

### 14.1 权限矩阵

- 所有者：查看全部版本，管理任意主题，编辑自己的正文，删除任意评论，解决、重新打开和重新关联任意主题。
- 实时协作者：在有效协作会话绑定的活动版本中创建、回复、管理自己的内容，解决自己发起的主题。
- 登录分享访客：使用当前账号身份，创建、回复、编辑和删除自己的内容，解决自己发起的主题。
- 匿名分享访客：使用版本级浏览器身份，拥有与普通分享访客相同的自有内容权限。
- 分享链接关闭评论后，通过该链接进入的访客只读；所有者内部权限不变。

### 14.2 版本级匿名身份

同一浏览器、同一 `version_id` 复用匿名身份，即使通过不同分享链接进入也可以管理自己以前的匿名评论。不同版本使用不同身份。服务端只存 secret 摘要，原始 secret 不进入日志、数据库明文或缓存键。登录后新评论使用登录身份，不自动认领旧匿名评论。

### 14.3 分享访问与 Realtime

评论访问令牌绑定：`version_id`、当前 `share_id` 或协作会话、principal、读写能力和过期时间。私有 Realtime 频道需要服务端授权，不能仅凭可枚举 ID 订阅。分享失效、密码变化、评论关闭或协作会话撤销后停止续签，已打开页面及时降级。

### 14.4 数据保护

- 评论表启用 RLS，但浏览器不直接写领域表；
- Service Role 只存在于 Edge Function；
- 所有写入重新验证版本、线程、父评论和 actor；
- revision/条件更新防止并发覆盖；
- 登录、匿名和同一分享入口分别限流；
- 服务端验证 Unicode 字素长度、锚点 schema 和安全链接；
- 错误只返回稳定 code、用户可读 message 和 request_id，不泄露数据库结构。

## 15. 迁移与发布

### 15.1 添加式迁移

本次迁移顺序：

1. 添加版本状态、当前版本指针、分享版本指针和评论版本指针；
2. 为每份在线简历创建或确定唯一活动版本，既有历史版本标记冻结；
3. 将工作区评论映射到活动版本；
4. 将历史评论映射到对应历史版本；
5. 将来源为 current 的分享链接和发布评论映射到活动版本；
6. 将带明确历史版本 ID 的分享映射到该历史版本；
7. 合并同版本的旧评论空间并重建 event seq；
8. 校验数量、作者、删除状态、解决状态、锚点和未读；
9. 服务端兼容新旧读取后切换客户端；
10. 验证稳定后停止旧路径写入。

不在本次迁移中删除旧列或旧 scope。旧字段清理必须通过以后单独审批的破坏性迁移。

### 15.2 评论合并

- 保留全部主题和评论，不按正文去重；
- 保留原始 ID、作者、时间、编辑和删除状态；
- 为新版本空间重建单调 event seq；
- 重算未解决、已解决、detached 和未读；
- 使用目标版本快照重新验证锚点；
- 记录 legacy scope 到 version scope 的迁移映射；
- 回填脚本幂等，重复执行不复制数据。

迁移期间允许有范围明确的兼容读取层，但最终运行态只有版本评论空间。

### 15.3 发布与回滚

按数据库、Edge Function、客户端顺序发布：

- 数据库先做纯新增与可回填迁移；
- Edge Function 同时支持旧客户端；
- 客户端通过开关切换新模型；
- 异常时关闭新读取路径，不删除新数据；
- 评论合并前后记录数量与映射；
- 不把不可逆字段删除和功能切换放在同一发布中。

## 16. 可观测性与错误处理

客户端为 Drawer 打开、bootstrap、来源加载、mutation、Realtime 补偿和正文同步记录 performance mark。Edge Function 为鉴权、访问解析、数据库读取、作者批量查询、写事务、事件发布分别记录耗时，并通过结构化日志或 `Server-Timing` 暴露非敏感分段。

每次请求拥有 `request_id`。慢请求记录操作、版本、阶段耗时、查询数量和结果规模，不记录评论正文、token 或匿名 secret。

来源加载、评论加载、权限失效、正文 revision 冲突、Realtime 断线和单项 mutation 使用不同错误 code，客户端据此决定保留缓存、保留草稿、回滚还是降级只读。

## 17. 验证方案

### 17.1 数据与权限

- 一份简历只能有一个 active 版本；
- 多分享链接同版本正文与评论一致；
- 创建新版本后旧链接停留旧版本，新版本评论为空；
- 当前版本云端同步成功后分享更新，失败时保持旧快照；
- owner、协作者、登录访客、匿名访客和只读链接无越权；
- 同浏览器匿名身份跨同版本链接可管理，跨版本不可管理；
- 迁移前后线程、评论、tombstone 和事件数量一致；
- 回填可重复执行且不重复数据。

### 17.2 实时与性能

- 编辑器和两个分享链接三窗口实时互通；
- 自己的写事件不重复插入；
- 断线后按 event seq 补偿；
- 正常写入无后续全量列表请求；
- 评论来源失败不阻塞当前版本；
- 记录并对比优化前后网络瀑布、请求数和分段耗时；
- 有缓存、无缓存、慢网和权限续期分别验证。

### 17.3 UI 与交互

- 编辑侧栏打开时书签不遮挡并停靠正确；
- 桌面 Drawer 从右侧、移动端统一从底部；
- 首次移动端打开无 snapPoint 警告且高度稳定；
- 短内容、长内容、键盘、横屏和安全区正常；
- 强高亮关闭后退回弱高亮；
- 任意递归回复在约 400px Drawer 和移动端不溢出；
- 删除有/无后代、解决成功/失败、来源切换和发送失败动画正确；
- `prefers-reduced-motion` 下没有多余位移和缩放；
- 键盘、焦点、aria-label 和 Tooltip 可用。

### 17.4 工程验证

- TypeScript；
- 评论相关定向 ESLint；
- 生产构建；
- Edge Function Deno check；
- 数据库迁移与 RPC 验证；
- `git diff --check`；
- 桌面浏览器自动或人工交互验证；
- iOS Safari 与 Android Chrome 真机验收单独记录。

静态检查、浏览器模拟和真机验证必须分别陈述。没有真实交互证据时，不得宣称对应移动端问题已经完全验收。

## 18. 实施原则

- 先建立版本领域不变量和迁移，再切换评论 API，最后改 UI，避免在错误数据边界上继续堆交互补丁。
- 任何性能优化都需用请求数量和阶段耗时验证。
- 任何乐观更新都必须有服务端校准和失败回滚。
- 任何动画都不能隐藏错误、阻塞操作或人为拖延请求。
- 保留现有分享、编辑、打印和 PDF 能力，评论层不进入导出。
- 实施计划按可验证的小阶段推进，每个阶段保持可构建并提供检查点。
