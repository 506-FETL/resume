# 简历打开正文传输验收

日期：2026-11-13。实施完成；下述验证完成；用户审查待进行。当前分支，没有提交或推送。前端修改在本地，数据库函数已部署到当前 linked Supabase 项目。

## 根因与证据

用户报告“全栈开发”打开明显变慢。本轮检查实际 Chrome → Supabase Data API → PostgreSQL → Automerge → 预览/表单链路，没有修改真实简历内容。

| 阶段                   | 列表进入编辑 | 编辑页直接刷新 |
| ---------------------- | -----------: | -------------: |
| 正文 GET 完整响应      |    23,939 ms |      17,295 ms |
| 收到响应头             |     4,320 ms |       2,351 ms |
| 解码与导入             |       330 ms |         225 ms |
| 导入后纸张正文首次出现 |    约 101 ms |      约 139 ms |

正文和外观请求已并发，WASM 没有阻挡正文请求。样本 SQL 的 EXPLAIN ANALYZE 为 2.369 ms；同期 Data API 日志 origin_time 为 412–612 ms，upstream 为 26–205 ms。这些服务端样本没有与每条浏览器请求逐 ID 配对，只用于确认数量级，不能从不同请求相减推导精确网络耗时。评论请求在正文出现后发生，实际 Edge 地区为 us-east-1；数据库地区也为 us-east-1。

主要等待是浏览器完整接收正文。该文档的真实 Automerge 二进制为 138,275 B；旧写入先转为 Base64 ASCII 后存入 bytea（184,368 B），表读取又将 bytea 转成十六进制 JSON，带字段名的 JSON 达 368,759 B。文档上次写入仍为 11 月 5 日，没有发现本轮之前近期改写导致的数据膨胀，不能把此次慢加载归因于最近的 UI 提交。

本机启用 127.0.0.1:7890 系统代理。用同一个公开模板目录做只读 curl 对照，直连两轮 1.75/1.50 s、代理两轮 1.75/1.84 s（gzip 约 22 KB）。该小样本没有支持“代理配置就是根因”的结论，也不是完整私有文档链路的替代测试。未修改网络设置。

## 最终实现

- 新增 `public.get_automerge_snapshot(uuid, uuid)`，返回 Base64 文本，消除 bytea 的十六进制包装。原生 Automerge bytea 根据既有魔数编码；历史 ASCII Base64 bytea 转回文本。
- 函数为 STABLE、SECURITY INVOKER、空 search_path，复用原 owner RLS（包括简历父记录的归属复查），只向 authenticated 授予执行权限。没有更改表/RLS/写入格式或真实数据。
- 原轻量 `readAutomergeSnapshot` 改用 GET RPC + maybeSingle。继续使用现有 SDK 认证刷新和幂等请求重试；null、undefined、请求失败及损坏文档仍沿原分支处理。
- 没有引入正文缓存，也没有更改旧保存队列、账户代次、guest bootstrap、离线加载、模板预取、分页和 UI 动效。这些调用边界经差异与代码审查核对；本轮没有重新执行完整双人协作、离线 UI 或所有历史账户切换矩阵。

独立审查发现初版默认 POST 会丢失 SDK 的临时错误重试，已改为 GET 并增加真实 SDK 的 503 重试验证；复核没有遗留 P1/P2。

## 新旧对照

同一 Chrome 登录会话、同一份真实简历，按 old/new/new/old/old/new 顺序读取，每组各 3 次。下列数值包括完整响应读取与 SDK 解析，不含编辑器绘制；浏览器、服务端和模板缓存未清空。开发服务变更及主动复测形成三个时段，分别列出，避免混合为固定提速承诺。

| 时段   | 旧接口中位数 | 新接口中位数 |
| ------ | -----------: | -----------: |
| 第一组 |     3,437 ms |     2,443 ms |
| 第二组 |     7,712 ms |     7,004 ms |
| 第三组 |     9,039 ms |     7,594 ms |

实际响应均带 `content-encoding: gzip`。同一浏览器 CompressionStream 对已读取的 JSON 重新压缩得到以下估算，**不是实测网络 transferSize**（跨源 ResourceTiming 未开放字节数）。

| 载荷口径                 |    旧接口 |    新接口 |
| ------------------------ | --------: | --------: |
| JSON，UTF-8 字节         | 368,759 B | 184,388 B |
| 相同 gzip 算法重压缩估算 | 166,716 B | 135,833 B |
| 解码后真实文档           | 138,275 B | 138,275 B |

JSON 减少约 50%，gzip 估算减少约 18.5%；不能宣称真实传输量减半。所有新旧响应解码后的 SHA-256 完全相同。另一次 gzip 核对请求为旧 10,559 ms、新 7,244 ms，依然存在明显公网波动。

最终完整开发编辑页的正文请求为 5,807 ms，导航后约 7,363 ms 出现正文，最终为两页；导入阶段仍有约 332 ms 长任务。实际打开“编辑简历”后，姓名、联系方式等真实表单可用，控制台无 error/warn。这个单次结果包含当时网络条件，不能与最慢基线直接相减当作代码收益。前端本身不能保证消除网络慢请求。
