调查状态：已完成报告解析、源码追踪、开发 sourcemap 核对和隔离慢网启动对照。产品修复状态：本轮没有修改业务代码，以下优化项尚未实施。用户审查：待进行。未提交、推送或发布。

## 2. 首要原因：首屏开发资源负担

手机报告中，在原始观测 FCP 225 ms 前已启动 190 个脚本请求，对应全部资源约 4.14 MB；原始 LCP 575 ms 前已启动 192 个脚本请求，对应约 4.20 MB。这是时间窗口内的请求统计，不代表这些资源全部是 LCP 的直接依赖。

关键资源包括：

| 资源                       | 报告传输字节 | 核查结果                                           |
| -------------------------- | -----------: | -------------------------------------------------- |
| `lucide-react.js`          |    588,510 B | 开发预构建包含图标库导出；生产打包才按实际引用裁剪 |
| `src/index.css`            |    520,594 B | 开发时作为 JS 注入；解码后的 CSS 为 492,065 B      |
| `react-dom_client.js`      |    354,425 B | React 开发运行库                                   |
| `react-router-dom.js`      |    198,188 B | 首屏路由运行时                                     |
| `@supabase_supabase-js.js` |    195,598 B | 认证与界面并行启动仍共享网络带宽                   |
| `@vite/client`             |    179,952 B | 开发客户端                                         |
| `@react-refresh`           |    112,187 B | 开发热更新运行时                                   |

直接请求当前开发服务器确认：CSS 模块和图标模块均没有 `Content-Encoding`，字节确实经网络传输，并非只统计磁盘解压大小。业务模块还包含 inline sourcemap：例如首页模块 56,169 B 中，32,386 B 是 inline map；快捷入口模块 43,297 B 中，21,194 B 是 inline map。

已有 `optimizeDeps.esbuildOptions.minify: true` 只压缩第三方预构建依赖，不能消除业务源码、开发运行库、inline sourcemap、CSS 注入和大量原生 ESM 请求。继续以“已压缩依赖”解释为完成，证据不足。

## 3. 生产仍有的成本：缩略图复用完整文档流水线

实际调用链：

`RecentResumeCard` 可见 → `ResumeThumbnail.acquire` → 预览 store 队列 → 动态导入生成器 → 读取完整正文 → `ScaledReadonlyPreview` → `CanonicalPagedDocument` → 等待字体与图片 → 完整分页 → 克隆第一页 DOM → 缓存 HTML。

对应代码：

- `src/pages/resume/store/preview-cache-state.ts`：`pump()` 只允许一个 active job，任务包含读取、字体等待和完整渲染；完成后才启动下一份。
- `src/pages/resume/components/resume-card/resume-focus-preview/generate-preview.tsx`：先等模块导入完成，再在生成函数内 `getAccessibleResumeById()`，随后挂载隐藏的 React root。
- `src/pages/resume/components/resume-card/resume-focus-preview/preview-generator/index.tsx`：完整文档 ready 后，通过 `querySelector('[data-resume-page]')` 只捕获第一页。
- `src/components/resume/pagination/canonical-paged-document.tsx`：按全部 `pageCount` 创建展示页，每页各区域插入正文组件，再用位移和 `overflow: hidden` 裁切；另有一份测量源。
- `src/pages/resume/components/resume-card/resume-focus-preview/index.tsx`：成品为 HTML，重新展示时继续使用字体和 DOM；不是已经脱离排版依赖的图片。

限制渲染并发有明确的历史目的，不能直接把完整渲染改为无限并发。但当前限制也把第二份正文的网络读取串行化，并且为只需要首页的缩略图渲染全部展示页。长文下，正文组件会随页数重复创建；具体 CPU 占比仍须使用同份长文 trace 做消融验证，不能仅凭代码推算毫秒收益。

手机报告的原始网络时序与此一致：

| 步骤                   | 导航后时间       |
| ---------------------- | ---------------- |
| 简历摘要响应完成       | 3.062 秒         |
| 缩略图模块开始加载     | 3.288 秒         |
| 生成器模块开始加载     | 3.602 秒         |
| 第一份完整正文         | 4.026 → 4.768 秒 |
| 第一批中文字体开始请求 | 4.860 秒         |
| 第二份完整正文         | 5.114 → 6.647 秒 |
| 第二批中文字体开始请求 | 6.757 秒         |
| 第二批字体响应结束     | 约 6.768 秒      |

两次正文读取的原始耗时分别约 742 ms 和 1,534 ms，彼此不重叠。浏览器记录可证明客户端串行依赖；这两份 HTML 报告不含数据库执行 trace，不能据此声称 SQL 慢、跨区或需要新增索引。

## 4. 字体告警指向预览，不等于标题被字体阻塞

24 个字体文件实际为 Inter 1 个、Tinos 2 个、Noto Sans SC 21 个。模板 CSS 声明很多字体，不等于浏览器下载了全部字体族；本次实际下载清单已逐项核对。Tinos 的中文回退来自 `getFontFamilyCSS()` 中显式配置的 Noto Sans SC。

首页说明使用 `Inter Variable / PingFang SC / Microsoft YaHei / system-ui`。报告中的 LCP 节点是“继续编辑简历，查看待办与求职进展。”，原始 LCP 为 575 ms；Noto 请求始于 4.86 秒和 6.76 秒。因此不能把网络依赖树末端字体的 6.779 秒写成该标题实际等待的时间，更不能直接解释为 27.305 秒模拟 LCP 的单一原因。

字体流量和预览等待都是真实成本。现有冷载预览需要排版全文，刷新后内存成品缓存失效，仍会重新读取、挂载、等待字体和测量。上一轮将这部分统称“必要字体”并停止追查，遗漏了缩略图生成方式本身的成本。

Lighthouse 默认模拟节流先采集原始加载，再预测受限条件下的指标；原始 trace、模拟分数和正文可用时间必须分别记录。[官方节流说明](https://github.com/GoogleChrome/lighthouse/blob/main/docs/throttling.md)

## 5. 强制重排是真问题，但不是全部阻塞

桌面报告定位到 `scaled-resume-document.tsx` 的重排为 33.080 ms；手机原始记录为 41.978 ms，另有 `use-mobile.ts` 的 30.938 ms。

源码位置：

- `scaled-resume-document.tsx:46`：ResizeObserver 回调又安排到下一次 rAF，随后同步读取 `canvas.offsetWidth`、`canvas.offsetHeight`、`viewport.clientWidth`。下一帧前其他 DOM 写入可以重新使布局失效；使用 rAF 并不保证这些读取不会触发布局。
- `use-mobile.ts:17`、`:24`、`:28`：初始化与 effect 重读 `window.innerWidth`，尽管已创建了 MediaQueryList。报告确实捕获到该调用点的同步布局成本。
- 缩略图生成使用固定 A4 容器，捕获的是未缩放纸页，仍经过展示用缩放测量。需要先核对消费者，评估能否绕开这层无用测量，或使用 ResizeObserver 已给出的尺寸。

手机主线程工作估计为 7.335 秒，其中 Script Evaluation 3.212 秒，Style & Layout 1.486 秒。React 运行时被归因的脚本时间约 2.552 秒。不能将其全部算成 React 自身或预览：这些运行时也执行其他组件工作，报告没有完整调用树。原始重排毫秒、经过 CPU 放大的主线程估计与模拟 TBT 839 ms 不能直接相减。

## 6. “重复 JavaScript 237 KiB”的主要条目误归类

报告把 29 个不同目录的 `index.tsx` 合并为同一来源，标记 217,080 B。对这些 URL 的当前开发响应逐个解码 inline sourcemap：

- 29 / 29 个 `sources` 都是 `["index.tsx"]`，没有 `sourceRoot`。
- 29 / 29 份 `sourcesContent` 的 SHA-256 均不同。
- 首页、快捷操作、统计卡、骨架、预览等是不同功能实现，没有证据表明这些整份组件可以删除为“重复模块”。

Chromium 的重复分析按 sourcemap 来源标识归组，不是直接比较全部业务代码内容。[官方分析实现](https://github.com/ChromeDevTools/devtools-frontend/blob/main/front_end/models/trace/extras/ScriptDuplication.ts)

此外，对报告列出的 Motion、React、Lodash、Dayjs、Zustand 共 15 个预构建文件读取当前 `.map`，得到 517 个不同的归一化来源路径，未发现这组文件间相同来源路径重复。这里核查的是当前开发响应，不是当时保存的全部 sourcemap；不能据此替整个生产构建作“绝无重复依赖”的保证。后续应以完整来源路径、实际模块内容和生产模块图确认，不能按包名或文件名机械合并代码。

## 7. 图片和缓存告警仅存在于桌面报告

两项告警指向同一个历史账户头像：512×512 图像、约 155 KB，在 32 CSS px 的位置展示，报告按 DPR 2 计算需求为 64×64；缓存 TTL 为 1 小时。图片预计节省 154,543 B，缓存预计节省 124,609 B，不能把二者相加成两份独立流量。

手机报告没有图片请求，这两项的 savings 都为 0。它们不能解释手机 35 分。

上一轮的 WebP 裁剪出口只影响新上传头像，不会自动改变当前账户已经保存的旧头像。因此桌面告警继续出现符合现状；后续若要覆盖旧资源，需要验证缩略图服务或显式迁移策略，不能仅修改新上传逻辑后宣称历史图像已优化。

## 8. 后续优化优先级与验收要求

1. **先固定验收环境与数据。** 保留开发服务体验诊断，但正式性能目标使用生产构建、同一份内容与字体，分别记录标题出现、创建入口可用、两张真实预览 ready。此前生产 81 分使用合成样本、16 个字体 / 905,704 B；本次用户报告为 24 个字体 / 1,313,668 B，不能拿旧分数证明当前问题消失。
2. **缩略图专用生成路径。** 在保留真实模板、字体、正文和分页结果的前提下，测量必要正文，只生成要展示的第一页，不生成随后丢弃的其他展示页，不进入无用的缩放流程。完整编辑与导出路径保持原协议。若使用图片成品，还需单独设计版本、权限、失效和更新机制，不在诊断阶段直接加入存储协议。
3. **将网络准备与串行渲染区分。** 测量可见目标的正文、精确模板和引擎是否能有界并发准备，保留一次只运行一个重排版任务的保护、账户代次和失败重试；不能取消归属确认或读取完整正文所需的校验。
4. **处理已定位的尺寸读取。** 缩略图绕开不必要缩放后，再核对共享缩放组件是否可用 ResizeObserver 的尺寸数据；手机断点沿用 MediaQueryList。与分页/打印相关的修改必须完成短文、临界页底、多页、默认模板及真实 PDF 导出验收。
5. **单独处理桌面旧头像。** 核对当前已存资源与新上传资源，两者分开验收，继续保留失败回退。
