# 公司与岗位流程重构设计

日期：2026-10-26。状态：核心规则由用户纠正并确认；本文件为重构审查稿，尚未迁移业务数据。动效修复独立实施，不以本计划替代动效验收。

## 取代的旧规则

此前第三期允许“同一岗位多次投递、共用进度”。用户本次明确纠正：同一岗位流程只有一次投递，结束后被捞回是接续流程；同公司是否允许多个同时进行的流程属于公司规则。旧设计的多次投递列表与再次投递入口不再作为后续实施依据。

用户补充确认：单流程公司同一时间最多一个进行中的岗位流程，结束后可以申请其他岗位。已有看板、列表、抽屉和三个页签继续保留。

## 模型与选择

推荐独立的公司档案，档案下管理岗位流程。公司拥有名称、Logo 和并行规则；岗位流程拥有岗位、批次、JD、阶段、下一步、联系人和面试记录。一条岗位流程最多一个投递事实，其材料允许后补。

仅按公司名称字符串分组虽然改动小，但简称、改名及同名公司会破坏规则校验，不采用。将所有流程压成一条公司进度又会丢失允许并行公司的岗位进展，也不采用。

- 公司并行规则为“未确认 / 同时一个 / 允许多个”，默认未确认，不猜测招聘政策。未知时允许记录真实流程，并提示用户可补充公司规则。
- 进行中指已投递、测评、筛选、笔试、面试；已保存不占名额，已结束和已录用沿用现有终态定义。归档只是显示状态，不能释放仍在进行的名额。
- 同一公司、同一招聘职位和批次只保留一个流程。岗位名称不是全局唯一键；不同部门、职位编号或明确的新批次可以建立不同流程。疑似重复先提示打开已有流程，不凭同名强制合并。
- 单流程公司开始另一岗位流程或恢复旧流程时，若已有进行中的流程，展示冲突流程并阻止提交；用户先明确结束原流程，或确认公司实际上允许并行后修改规则。不得静默关闭、归档或覆盖原流程。

## 投递、材料与阶段

“已投递”仍是流程中的阶段，进入该阶段就是确认一次投递事实。日期、渠道、提交材料都是该事实的详情，不再形成另一条独立进度。

1. 已保存 → 已投递：沿用现有推进动作，可填写日期和渠道；材料可暂缺，不能阻断真实进度记录。
2. 后续阶段查看“已投递”：展示同一次投递信息，可补充未知信息；补材料或纠错不退回已投递，不增加投递次数。
3. 联系人与简历页保留准备中的简历，下面改为“已提交材料”摘要；链接到同一投递详情。移除可无限新增的“投递记录 / 再次投递”列表。
4. 准备中的简历继续可编辑；实际提交的平台版本或 PDF / DOCX 保持快照，后续编辑原稿不改历史。纠错需显式操作并留下修改记录。
5. 创建简历、下载文件、创建分享都不自动变成投递。补录未知日期保留未知，不能用录入时间冒充投递时间；原岗位没有可靠投递历史时也不能自动补造。

## 结束后被捞回

“已结束”增加“恢复面试流程”动作，记录恢复日期、原因及目标阶段，保留此前终止事实、阶段与面试笔记。面试轮次继续追加，不产生第二次投递，也不重置原投递材料。

原岗位继续面试复用原流程。被推荐到不同岗位时在同公司下建立新的关联流程，记录“来自原流程转岗 / 推荐”，不把它伪装成原岗位再次投递；若没有新的实际投递，来源事件明确标为推荐，投递日期为空。单流程限制仍适用。恢复归档流程必须显式说明并取消归档，避免恢复后不可见。

## 界面与统计

- 列表可按公司分组，在公司标题显示进行中流程数量和规则；每个岗位仍为独立行。看板仍按阶段展示岗位卡，卡上保留公司名，可通过公司筛选查看关联流程。
- 抽屉头部显示公司和岗位，增加查看同公司流程的轻量入口，不新建独立公司工作台，不替换现有三个页签。
- 已投递阶段详情承担投递事实编辑；联系人与简历中的材料摘要复用同一数据。首页待补材料按流程去重。
- 当前阶段计数继续按岗位流程计算；公司数量单独标注，不混用。被捞回不增加历史投递数量；响应率继续按有真实投递依据的流程去重，不按材料修改或恢复次数计算。

## 数据改造与历史保留

现有 public.company 实际上一行一个岗位流程，保留现有 ID 与简历、分享、岗位上下文关联。新增账户内公司档案 tracker_companies，并在旧流程记录增加公司引用；业务类型继续使用 JobApplication，避免无关改名。

job_submissions 当前允许一个 job_id 对应多行。先只读统计实际重复与材料，再转换为“一条主投递事实 + 原历史凭据”。旧多条记录原文、文件和时间均保留，不选最新覆盖其他记录、不删除文件、不自动拆成虚构招聘流程。多条数据无法无歧义归并时，让用户在既有流程中确认主事实；确认前只读展示旧记录并禁止继续追加。

公司归并仅在同账户内进行。完全一致的既有公司名称可生成建议分组；简称、同名公司和已存在多个进行中流程不能静默合并并施加单流程限制。迁移默认规则未确认，保留所有真实流程；用户选择单流程时必须先解决已有冲突。

服务端同一事务校验所属账户、一次投递唯一性及公司活跃流程名额。开始 / 恢复 / 改公司 / 改规则均走同一约束，不能仅禁用前端按钮。重复提交使用稳定操作身份；两个标签并发申请时最多一个成功，失败保留原流程和输入。

## 验收与交付边界

覆盖一个公司两个岗位的单流程阻止与多流程允许、已保存不占名额、归档仍占名额、结束后申请其他岗位、被捞回保留历史、单流程恢复冲突、转岗来源、未知投递日期、补材料不回退、多次点击和双标签并发、旧多条记录无损保留、账户隔离与文件权限。

数据库 / Edge Functions 实施获准后，必须完成隔离迁移演练、保留数据指纹对照、云端部署、迁移账本与函数版本核验、线上正向及跨账户 smoke。此轮只交付可审查的重构设计和实施顺序，不提前执行数据迁移。
